# Claude Code는 로컬에서 어떻게 동작하는가

[[README|← Claude 활용법]]

> 이 문서는 Claude Code 자신이 자기 동작 방식을 설명한 것 (2026-07-13 기준).
> 핵심 한 줄: **모델(두뇌)은 클라우드에, 손발(도구 실행)은 내 PC에 있다.**

## 1. 전체 구조

```
┌─ 내 PC ──────────────────────────────┐        ┌─ Anthropic 클라우드 ─┐
│  Claude Code (CLI/VSCode 확장)        │        │                      │
│  = "하네스(harness)"                  │ ←────→ │   Claude 모델         │
│  - 대화 관리, 컨텍스트 조립           │  HTTPS  │   (추론만 함.         │
│  - 도구 실행 (파일, 셸, 검색)         │        │    PC에 접근 불가)    │
│  - 권한 검사, 세션 저장               │        │                      │
└──────────────────────────────────────┘        └──────────────────────┘
```

- **모델은 내 파일을 직접 못 본다.** 모델이 "이 파일 읽고 싶다"고 요청(tool call)하면,
  로컬 하네스가 실제로 파일을 읽어 그 내용을 다음 요청에 담아 보내준다.
- 반대로 모델의 모든 행동(파일 수정, 명령 실행)도 하네스가 대행한다.
  → 그래서 권한 시스템이 하네스 쪽에 있다.

## 2. 에이전트 루프 (핵심 매커니즘)

Claude Code의 본질은 단순한 반복문이다:

```
사용자 메시지
   ↓
[모델 호출] ← 시스템 프롬프트 + 지금까지의 대화 전체 + 도구 목록
   ↓
모델 응답 = 텍스트 and/or 도구 호출(tool call)
   ↓
도구 호출이 있으면 → 하네스가 로컬에서 실행 → 결과를 대화에 추가 → 다시 [모델 호출]
도구 호출이 없으면 → 턴 종료, 사용자에게 최종 텍스트 표시
```

- "파일 3개 읽고 → grep 하고 → 수정하고 → 테스트 돌리는" 작업은
  이 루프가 수십 번 도는 것. 매번 **대화 전체가 다시 전송**된다 (모델은 무상태).
- 같은 응답 안에서 독립적인 도구 여러 개를 **병렬 호출**할 수도 있다.

## 3. 도구 (모델의 손발)

| 도구 | 하는 일 |
|---|---|
| Read / Write / Edit | 파일 읽기/생성/부분 수정 (Edit는 정확한 문자열 매칭 치환) |
| Glob / Grep | 파일명 패턴 검색 / 내용 검색 (ripgrep 기반) |
| Bash / PowerShell | 셸 명령 실행 (git, npm 등). 백그라운드 실행도 가능 |
| Agent | 서브에이전트 생성 — 별도 컨텍스트를 가진 "새 Claude"에게 하청 |
| Skill | 스킬(작업 매뉴얼) 로드 |
| WebSearch / WebFetch | 웹 검색/페이지 가져오기 |

- 각 도구 호출은 **권한 규칙**을 통과해야 실행됨 (아래 6절).
- MANAGE 개발 때 "vite HMR 로그 파일을 Read로 확인"하던 것 = 백그라운드 Bash의 출력 파일 읽기.

## 4. 컨텍스트 조립 — 모델이 매번 받는 것

모델 호출 한 번에 들어가는 내용 (이게 곧 "모델이 아는 전부"):

1. **시스템 프롬프트** — 하네스가 자동 생성: 작업 디렉토리, OS, git 상태, 날짜 등
2. **CLAUDE.md** — 프로젝트/전역 지침 (사용자가 작성한 규칙)
3. **메모리** — `~/.claude/projects/<프로젝트>/memory/MEMORY.md` 인덱스가 매 세션 로드됨.
   개별 메모리 파일은 필요할 때 읽음. (세션이 끝나도 남는 유일한 "기억")
4. **스킬 목록** — 이름+설명만 로드, 본문은 Skill 도구로 호출해야 로드
   (예: 오늘 만든 `.claude/skills/manage-ui/SKILL.md`)
5. **대화 이력** — 이번 세션의 모든 메시지 + 도구 호출/결과

**컨텍스트 윈도우는 유한**하다. 꽉 차면 하네스가 과거 대화를 **요약(compaction)**으로 압축해
이어간다 → 오래된 세부사항은 요약 수준으로만 남는다. 그래서 세션을 넘겨 기억할 것은
메모리/CLAUDE.md/스킬에 **파일로** 박아야 한다.

## 5. 로컬에 저장되는 것들 (`~/.claude/`)

```
C:\Users\diffi\.claude\
├─ settings.json              # 전역 설정/권한
├─ projects\
│   └─ c--...-Project-MANAGE\
│       ├─ *.jsonl            # 세션 transcript (대화+도구호출 전체 기록)
│       └─ memory\            # 프로젝트 메모리 (MEMORY.md + 개별 파일)
└─ skills\                    # 전역 스킬

각 프로젝트 폴더\
└─ .claude\
    ├─ settings.json          # 프로젝트 권한/설정
    └─ skills\manage-ui\SKILL.md   # 프로젝트 스킬
```

- **transcript(.jsonl)**: 한 줄 = 한 이벤트(유저 메시지, 모델 응답, 도구 결과…).
  "과거 세션 피드백 164건 분석"이 가능했던 이유 = 이 파일을 직접 파싱한 것.
- 세션 자체는 로컬 파일일 뿐이라, Claude Code가 스스로 읽으면 "과거 기억"처럼 쓸 수 있다.

## 6. 권한 시스템

- 모든 도구 호출은 실행 전 권한 검사: **allow 규칙 매칭 → 자동 실행 / 아니면 사용자에게 물음**.
- 규칙은 `settings.json`의 allowlist (예: `Bash(git status:*)` 허용).
- 모드: 기본(매번 확인) / auto-accept / plan mode(읽기만) 등.
- 거부하면 모델은 "거부됐다"는 결과를 받고 다른 방법을 찾는다.

## 7. 스킬과 메모리 — "학습"의 실체

모델 가중치는 대화로 안 바뀐다. Claude Code의 "성장"은 전부 **파일**이다:

| 수단 | 언제 로드 | 용도 |
|---|---|---|
| CLAUDE.md | 매 세션 자동 | 항상 지켜야 할 프로젝트 규칙 |
| 메모리 (memory/) | 인덱스는 자동, 본문은 필요시 | 세션 간 사실 기억 |
| 스킬 (SKILL.md) | 설명이 트리거되면 본문 로드 | 특정 작업의 매뉴얼/체크리스트 |

→ "피드백을 이미 내부적으로 갖추고 동작하게 하기" = 피드백을 스킬로 증류해두는 것.
(manage-ui 스킬이 정확히 이 사례)

## 8. 서브에이전트 / 백그라운드

- **Agent 도구**: 독립 컨텍스트의 새 Claude 인스턴스를 생성해 하청.
  본체 컨텍스트를 아끼면서 대량 탐색/병렬 작업 가능. 결과 텍스트만 본체로 돌아옴.
- **백그라운드 Bash**: dev 서버처럼 오래 도는 프로세스는 백그라운드로 띄우고
  출력 파일을 나중에 Read로 확인 (MANAGE에서 `npm run dev`가 이 방식).

## 9. MANAGE 개발에서 실제로 쓰인 조합 (사례)

1. `npm run dev` 백그라운드 실행 → HMR 로그 파일을 Read로 에러 감시
2. Grep으로 렌더 위치 전수조사 → Edit 병렬 다발 수정
3. 세션 transcript(jsonl) 파싱 → 피드백 164건 추출 → 스킬로 증류
4. 메모리에 `data-hl` 컨벤션 기록 → 다음 세션에서 자동 회상
