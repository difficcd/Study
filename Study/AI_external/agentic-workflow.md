# 에이전틱 워크플로우 교본

Easy MV Maker를 Claude Code로 작업하면서 **실제로 겪은 것**만 담았습니다.
일반론이 아니라 통한 것과 실패한 것의 기록입니다.

---

## 0. 한 줄 요약

에이전트에게 필요한 건 더 좋은 프롬프트가 아니라 **틀릴 때 알아차릴 수 있는 환경**입니다.
좋은 프롬프트는 좋은 시도를 만들고, 좋은 환경은 나쁜 시도를 걸러냅니다. 후자가 훨씬 큽니다.

# Part 1 — 기반

## 1. "빌드 통과"는 증거가 아니다

실제로 있었던 일:

> 리팩토링 중 모달 컴포넌트 두 개에서 `return`이 빠졌습니다.
> **빌드 통과, `tsc` 통과, UI 문자열 diff 통과, 커스텀 검증 스크립트까지 통과.**
> `undefined`를 반환하는 컴포넌트는 합법적인 React이고 유효한 JS이기 때문입니다.
> 화면에 아무것도 안 나오는데 모든 자동 검사가 초록불이었습니다.

검증 계층은 이렇게 쌓입니다. 위로 갈수록 강합니다:

| 계층 | 잡는 것 | 놓치는 것 |
|---|---|---|
| 빌드 | 문법, import 오류 | 거의 전부 |
| 타입체크 | 시그니처 불일치 | 런타임 동작 |
| 단위 테스트 | 순수 로직 | 배선, 렌더 |
| 계측(측정) | 성능, 메모리 | 시각적 정확성 |
| 사람의 눈 | 나머지 전부 | (느림) |

**"다 했습니다"라고 말할 자격을 주는 건 아래 두 계층입니다.**

## 2. 순수 함수로 밀어내기 — 테스트 가능한 표면 만들기

에이전트가 자기 작업을 검증하려면 **검증 가능한 코드**가 있어야 합니다.
컴포넌트 안에 박힌 로직은 브라우저 없이 확인할 방법이 없습니다.

이 프로젝트: 4,480줄 컴포넌트에서 순수 로직을 **14개 모듈**로 빼냈습니다.
테스트 0개 → **240개** (Node 내장 러너, 프레임워크 의존성 0).

요령은 **불순한 부분을 인자로 받는 것**:

```js
// 나쁨: 컴포넌트 밖으로 못 나감
const measureTextBox = (t) => { const ctx = measureCtxRef.current; ... }

// 좋음: 컨텍스트를 받으니 가짜로 테스트 가능
export function measureTextBox(t, measureCtx) { ... }
```

- `cloneCutContents(cut, cloneBitmapId)` — 비트맵 복사기를 주입
- `loadKeymap(storage)` — localStorage를 주입
- `drawTextObject(ctx, ...)` — **기록용 가짜 컨텍스트**로 *그리는 순서*를 검증

마지막이 특히 유용했습니다. 가짜 ctx가 호출을 기록하니:

```js
assert.ok(n.lastIndexOf('strokeText') < n.indexOf('fillText'),
    '외곽선이 모든 줄에 대해 채우기보다 먼저');   // 아니면 윗줄 디센더를 덮음
```

픽셀을 눈으로 봐서는 못 잡는 종류입니다.

### 폴더로 규칙을 강제하기

```
src/
  core/     순수 로직 — React·DOM·canvas 금지. 전부 테스트 있음
  canvas/   그리기. 넘겨받은 컨텍스트 외엔 순수
  ui/       컴포넌트
  hooks/    상태와 동작을 잇는 훅
```

**폴더가 냄새 감지기가 됩니다.** `core/`의 파일이 React를 import하면
"폴더가 틀렸거나, 그 부분은 인자로 받았어야 한다"는 신호입니다.

## 3. 추측하지 말고 계측하라

가장 값비싼 교훈.

브라우저가 OOM으로 죽었습니다. **코드를 읽고 가설 4개를 세워 전부 기각**했습니다.
특히 마지막이 함정이었습니다 — 캔버스 **객체**는 재사용되고 있었거든요:

```js
const cnv = hit || document.createElement('canvas');  // 재사용 ✓
cnv.width = CANVAS_W;   // ← 여기서 8MB 버퍼를 새로 할당
```

`canvas.width` 대입은 **값이 같아도** 백킹 스토어를 재할당합니다.
읽어서는 안 보입니다. 프로토타입 세터를 가로채니:

```
widthSets:      100      ← 10초간
sameValue:      100      ← 100번 전부 "이미 그 값인데 또 대입"
bytesRealloc:   791 MB   ← 초당 79MB
```

**세터 가로채는 데 5분, 그걸로 즉시 끝.**

### 성능은 변수 하나만 바꿔 판별하라

남은 렉이 React 리렌더인지 캔버스 래스터화인지 몰랐습니다.
**효과는 켠 채로 획 수만** 0개 vs 15개로 바꿨습니다:

| 조건 | p95 프레임 |
|---|---|
| 효과 ON, 획 0개 | 10.3 ms |
| 효과 ON, 획 15개 | **27.8 ms** |

획이 없으면 비용 0 → **리렌더는 무죄.** 이 실험 없이 렌더 경로를 리팩토링했다면 헛수고였을 겁니다.

## 4. 회귀 가드

에이전트는 지적하지 않으면 조용히 품질을 떨어뜨립니다. **기계적 가드**를 두세요.

`scripts/hook-baseline.mjs`가 React hooks 린트 경고 **개수**를 지킵니다.
줄면 통과, 늘면 실패.

실제로 잡혔습니다. 히스토리 로직을 함수로 묶었더니 effect가 그 함수를 참조하게 되어
경고가 10 → 11로 늘었습니다. 가드가 없었으면 그냥 통과했을 겁니다.
(해법: ref 경유. 의존성에 넣으면 매 렌더마다 effect가 다시 돕니다.)

**만들 만한 가드:** 린트 경고 개수 / 번들 크기 상한 / **테스트 개수가 줄면 실패**
(에이전트가 테스트를 지워 통과시키는 것 방지) / 커버리지 하한

하나로 묶어 **"완료" 선언 전 필수**로:
```json
"check": "npm run typecheck && npm test && node scripts/hook-baseline.mjs && npm run build"
```

## 5. 컨텍스트 인수인계 — 세션은 반드시 끊긴다

세 곳에 나눠 남깁니다:

**1) 저장소 안 (`ARCHITECTURE.md`)** — 코드 맵. 파일 목록보다 **함정**이 값집니다:
> - `canvas.width = n`은 n이 같아도 백킹 스토어를 재할당한다
> - 포인터 캡처는 *throw*한다. optional chaining으로 못 막는다
> - 상태 업데이터 안에서 일하지 마라 — StrictMode에서 두 번 실행된다

세 줄이 각각 실제 버그 하나씩입니다.

**⚠️ 문서가 틀리면 없느니만 못합니다.** 이 프로젝트의 문서는 캔버스를 854×480(실제
1920×1080)이라 하고, 이미 있는 비트맵 수집기를 "없다"고 적어뒀습니다.

**2) 에이전트 메모리** — 사람에 대한 것, 선호, 왜 그렇게 정했는지.
코드에서 유추 불가능한 것만. 코드 구조를 넣으면 금방 틀립니다.

**3) 커밋 메시지** — *왜*를 남기는 가장 좋은 곳. 코드와 함께 영원히 갑니다.

**나쁨:** `fix: canvas reallocation`
**좋음:** 증상 → 측정 → 원인 → 왜 그 해법인지

## 6. 역할 분담을 명시하라

세션 중 두 번 바뀌었고 두 번 다 이유가 있었습니다:

1. **"브라우저 금지, 테스트는 내가"** → 모달 `return` 누락으로 실패
2. **"직접 열어서 확인해"** → 반대로 과했음. 사용자가 어차피 볼 걸 재확인하느라 낭비
3. **현재: "진단·계측은 에이전트, 검증은 사람"**

**경계선:** 에이전트가 브라우저를 쓰는 건 **사용자가 알 수 없는 걸 알아낼 때**입니다
(크래시 재현, 원인 계측, 메모리·프레임 측정). 완성물 확인용이 아닙니다.

**신호:** UI 상태를 만들려고 Playwright 스크립트를 길게 짜고 있다면 넘길 때입니다.

**⚠️ 부작용:** 이 세션에서 제 테스트 낙서("DRAGME" 텍스트 등)가 **사용자의 자동저장
슬롯**에 들어갔습니다. 격리된 데이터로 돌리거나, 최소한 발생하면 즉시 알리세요.

## 7. 상태 계층이 리팩토링의 병목이다

"컴포넌트가 4,000줄"은 증상이지 병이 아닙니다.

진짜 이유: `setCuts`를 클로저로 잡은 핸들러는 **`setCuts`를 넘길 수 있는 곳으로만**
옮길 수 있습니다. 훅으로 빼면 의존성 20개짜리 객체가 되어 줄만 옮기게 됩니다.

해법은 **상태 컨테이너**. `cuts`를 `useReducer`로 옮기고 40여 개 람다를
이름 있는 액션 20개로 바꿨습니다:

```js
// 오타를 tsc가 잡도록 액션은 "생성 함수"로
export const updateCut = (cutId, patch) => ({ type: 'updateCut', cutId, patch });
```

문자열 리터럴이면 오타가 **조용한 no-op**, 함수면 타입 에러입니다. 실제로 4곳에서 잡혔습니다.

**덤:** 불변식을 한곳에서 강제할 수 있습니다. 레이어를 옮기면 `rev`를 올려야 캐시가
무효화되는데, 이제 액션의 일부라 **기억할 필요가 없습니다.**

# Part 2 — 자동화 수준별 방식

## 8. 자동화 스펙트럼

| 단계 | 방식 | 사람의 개입 | 맞는 일 |
|---|---|---|---|
| 0 | **자동완성** (Copilot 류) | 매 줄 | 타이핑 절약 |
| 1 | **대화형 페어링** | 매 턴 | 설계가 걸린 일, 원인 불명 버그 |
| 2 | **위임** | 시작·검수 | 범위가 명확한 작업 (이슈 하나) |
| 3 | **비동기 위임** | 검수만 | 여러 건 병렬, 백그라운드 |
| 4 | **완전 자동화** | 예외 시에만 | 반복·기계적·되돌리기 쉬운 것 |

### 핵심 규칙 하나

> **자동화 수준은 검증 가능성을 넘을 수 없다.**

자동으로 확인할 수 없는 것은 자동으로 맡길 수 없습니다.

| 작업 | 기계 판정 | 안전한 수준 |
|---|---|---|
| 순수 함수 리팩토링 | 테스트 240개 | **4 (완전 자동)** |
| 의존성 업데이트 | `npm run check` | **4** |
| 오타·문서 수정 | 빌드 | **3~4** |
| UI 레이아웃 수정 | ✗ 눈으로만 | **1~2** |
| "렉이 걸려요" | ✗ 원인 불명 | **1** |

렌더링·조작감처럼 판정이 사람 눈에 달린 것은 도구가 좋아져도 1~2단계입니다.

## 9. 단계 2 — 위임형: 이슈를 스펙으로

**"이슈 #12 해줘"** 가 되려면 이슈가 스펙이어야 합니다:

- **재현 절차** = 고쳤는지 판정하는 기준
- **완료 기준** = 언제 멈출지
- **하지 않을 것** = 스코프 크립 방지

세 번째가 중요합니다. 에이전트는 인접 문제를 같이 고치려 들고,
좋아 보이지만 **PR이 리뷰 불가능한 크기가 됩니다.**

```
이슈 #12를 해결해줘.
- 브랜치는 fix/12-…
- 끝나면 npm run check 통과 확인하고 PR 열어줘
- 이슈 범위 밖은 건드리지 말고, 발견하면 새 이슈로 남겨줘
```

마지막 줄이 스코프 크립을 **버리는 대신 기록**으로 바꿉니다.

## 10. 단계 3~4 — 자동 실행 방식들

### (a) CI에서 실행 — 가장 실용적

PR이 열리면 에이전트가 diff를 읽고 리뷰를 답니다.

**왜 안전한가:** 코멘트만 답니다. 코드를 안 바꾸니 최악이 "쓸데없는 리뷰"입니다.
자동화의 첫 단계로 위험 대비 효용이 가장 좋습니다.

### (b) 이슈 → 자동 PR

라벨이 붙으면 에이전트가 브랜치를 만들고 작업해 PR을 엽니다. **병합은 사람이.**

`agent-ok` 같은 라벨로 **명시적으로 표시한 이슈만** 대상으로 하세요.
전부 자동으로 두면 애매한 이슈에서 엉뚱한 걸 만듭니다.

### (c) 스케줄 실행

- 의존성 업데이트 + `npm run check` + PR
- 린트 경고 기준선 정리
- 죽은 코드·미사용 export 찾아 이슈 등록
- **문서와 코드 불일치 검사** ← 이 프로젝트에 실제로 필요했던 것

`ARCHITECTURE.md`의 캔버스 크기가 틀린 걸 몇 달 만에 발견했습니다.
"문서에 적힌 상수가 코드와 같은지"는 기계가 할 수 있습니다.

### (d) 워치독 / 자가 복구

배포 실패, CI 깨짐, 에러 급증에 반응.
**진단해서 이슈를 남기는 것까지**가 안전선입니다. 프로덕션을 자동으로 고치게 두면
사고 시 원인 파악이 훨씬 어려워집니다.

## 11. 병렬화 — 서브에이전트

**탐색 병렬화 (안전):** "이 세 곳에서 X를 찾아줘"를 나눠 던지고 결과만 모읍니다.
읽기만 하니 충돌 없음.

**작업 병렬화 (위험):** 여러 에이전트가 같은 저장소를 고치면 서로 밟습니다.
**작업트리 분리** 필요 (git worktree — 브랜치별 별도 디렉터리).

### 병렬이 오히려 손해인 경우

각 에이전트는 **맥락을 처음부터 다시 쌓습니다.** 이미 아는 걸 다시 파악하는 비용이
병렬로 버는 시간보다 클 때가 많습니다.

기준: **결론만 필요하고 과정이 길면** 병렬. **내 맥락이 필요하면** 직접.

## 12. 자동화의 안전장치

수준이 올라갈수록 이게 전부입니다.

**1) 되돌릴 수 있게.** 에이전트는 브랜치에서만, main은 PR로만.
squash 병합이면 PR 하나를 통째로 revert할 수 있습니다.

**2) 관문을 기계가.** `npm run check`를 CI에서 강제. 로컬에서 통과했다는 에이전트의
말은 증거가 아닙니다 — **직접 확인하세요.** 이번 세션에서 제가 한 번 잘못 보고했습니다
("301MB 누수"), 최신 스냅샷 하나만 본 결과였습니다.

**3) 권한을 좁게.** 토큰으로 할 수 있는 일 = 사고 시 피해 범위.
force push, 브랜치 삭제, 릴리스 발행은 빼세요.

**4) 사람 데이터에서 격리.** (6절의 자동저장 오염 사례)

**5) 되돌리기 쉬운 것부터.** 문서 → 테스트 → 리팩토링 → 기능 → 데이터 마이그레이션
순으로 어려워집니다. **마지막 것은 자동화하지 마세요.**

## 13. 컨텍스트 엔지니어링 — 자동화의 진짜 병목

자동화가 실패하는 흔한 이유는 모델이 멍청해서가 아니라 **맥락이 없어서**입니다.
프롬프트를 다듬는 것보다 여기에 투자하는 게 효과가 큽니다.

**1) 프로젝트 규칙 파일** (`CLAUDE.md`) — 빌드 명령, 코딩 규칙, "이건 하지 마라".
**짧게.** 길면 안 읽히고, 틀린 게 섞이면 해롭습니다.

**2) 코드 맵** (`ARCHITECTURE.md`) — 어디에 뭐가 있는지 + **함정**.

**3) 기억** — 사람·선호·결정 이유. 코드에서 유추 불가능한 것만.

**이 셋은 반드시 낡습니다.** 그래서 10(c)의 "문서-코드 불일치 검사"가 실제로 필요합니다.

## 14. 도입 순서 — 실제로 추천하는 경로

한꺼번에 하지 마세요. 각 단계가 다음 단계의 안전장치입니다.

```
1. npm run check 하나로 관문 만들기      ← 없으면 나머지 전부 무의미
2. 순수 로직 분리 + 테스트                ← 검증 가능한 표면
3. CI에서 관문 강제
4. 회귀 가드 (경고 개수, 번들 크기)
5. 브랜치 + PR 흐름
6. ARCHITECTURE.md + CLAUDE.md
7. ── 여기까지가 기반. 이제 자동화가 안전해짐 ──
8. PR 자동 리뷰 (코멘트만)
9. 라벨 붙은 이슈 → 자동 PR (병합은 사람)
10. 스케줄 작업 (의존성, 문서 검사)
```

**7번 앞에서 멈춰도 충분합니다.** 대부분의 이득은 1~6에서 나옵니다.
8번 이후는 반복 작업이 실제로 많을 때만 값어치가 있습니다.

## 15. 흔한 실패와 대처

**테스트를 고쳐서 통과시킴** → 테스트 개수가 줄면 CI 실패하게. 리뷰에서 테스트 변경을 유심히.

**PR이 리뷰 불가능한 크기** → 이슈에 "하지 않을 것"을 쓰고, "발견하면 새 이슈로".

**같은 버그를 반복해서 고침** → 검증 방법이 틀린 겁니다. 텍스트 크기 입력 버그를
세 번 고쳤고 매번 원인이 달랐습니다: (1) 키 입력마다 clamp → (2) blur 시 clamp →
(3) **포커스 도둑질**. 1·2 때 브라우저에서 직접 쳐봤다면 3을 바로 봤을 겁니다.

**"다 했습니다"인데 안 됨** → 완료 기준을 기계 판정 가능하게.
"동작합니다" 대신 "테스트 N개 통과, 측정값 X→Y".

**맥락이 길어져 품질 저하** → 작업 단위를 작게. 각 단계가 `check` 통과 상태로 끝나면
언제 끊겨도 안전합니다.
