

# CI/CD

**CI/CD**는 소프트웨어 개발에서 코드의 작성부터 배포까지의 과정을 자동화하여 효율성을 높이는 현대적인 개발 방법론입니다. 약어는 각각 지속적 통합(Continuous Integration)과 지속적 배포/전달(Continuous Delivery/Deployment)을 의미합니다.

### 1. CI (Continuous Integration - 지속적 통합)

개발자들이 작성한 코드를 빈번하게(하루에도 여러 번) 중앙 원격 저장소에 **통합**하는 과정입니다.

- **핵심 목표:** 코드 충돌을 사전에 방지하고, 버그를 조기에 발견하여 코드의 품질을 유지합니다.
    
- **주요 과정:**
    
    1. 개발자가 코드를 수정하여 저장소에 푸시(Push)합니다.
        
    2. 자동으로 **빌드**와 테스트(단위/통합 테스트)가 실행됩니다.
        
    3. 테스트를 통과하면 문제없이 통합되고, 실패하면 즉시 피드백을 받아 수정합니다.
        

### 2. CD (Continuous Delivery / Continuous Deployment - 지속적 전달 / 지속적 배포)

CI 과정을 거쳐 정상적으로 빌드된 코드를 사용자에게 **배포**하는 과정을 자동화하는 것입니다.

- **Continuous Delivery (지속적 전달):** 코드가 항상 배포 가능한 상태를 유지하도록 보장하는 것입니다. 실제 운영 환경으로의 배포는 최종적으로 **사람의 승인**을 거쳐 진행됩니다.
    
- **Continuous Deployment (지속적 배포):** 테스트를 통과한 코드가 사람의 개입 없이 **자동으로 운영 환경(실제 서비스)까지 배포**되는 단계입니다.
    

### 3. 도입 시 주요 장점

- **생산성 향상:** 수동으로 하던 빌드, 테스트, 배포 작업을 자동화하여 반복적인 수고를 줄입니다.
    
- **빠른 피드백:** 버그나 오류를 조기에 발견할 수 있어 수정 비용과 시간이 크게 줄어듭니다.
    
- **안정성 확보:** 철저한 자동 테스트를 거치기 때문에 배포 과정에서 발생할 수 있는 휴먼 에러를 방지합니다.
    

> **대표적인 CI/CD 도구:** GitHub Actions, GitLab CI/CD, Jenkins, ArgoCD 등



# GitHub Actions

**GitHub Actions**는 GitHub에서 직접 제공하는 **CI/CD(지속적 통합 및 배포) 자동화 도구**입니다.

학부 3학년 수준에서 개인 프로젝트나 팀 프로젝트를 진행하실 때, GitHub에 코드를 올리면(Push) 서버가 알아서 빌드도 해주고 테스트도 돌려주는 '나만의 자동화 비서'라고 생각하시면 아주 이해하기 쉽습니다.

### 1. 왜 사용하게 될까요? (기존 방식과의 차이)

보통 코드를 수정하고 배포하려면 다음과 같은 과정을 거치게 됩니다.

1. 로컬 환경에서 코드 수정
    
2. 빌드(`npm run build`나 `gradlew build` 등)가 잘 되는지 직접 확인
    
3. 테스트 코드도 직접 실행해 봄
    
4. 서버에 직접 접속하여 수동으로 파일 업로드 및 배포
    

이러한 과정을 **GitHub Actions**를 사용하면, 코드를 `git push`하는 순간 **GitHub 클라우드 서버에서 위 모든 과정을 알아서 백그라운드에서 실행**해 줍니다.

### 2. 주요 장점 (학부생 프로젝트 기준)

- **무료 이용:** 퍼블릭(Public) 저장소는 물론, 프라이빗(Private) 저장소에서도 개인 공부 용도로 충분한 무료 사용량(월 2,000분)을 제공합니다.
    
- **별도의 서버 불필요:** Jenkins 같은 전통적인 도구는 직접 서버를 구축하고 관리해야 하지만, GitHub Actions는 GitHub 내장 기능이라 설정 파일 하나만 올리면 바로 사용할 수 있습니다.
    
- **다양한 환경 지원:** 자바/스프링, 리액트/노드, 파이썬 등 전 세계 개발자들이 만들어 둔 검증된 템플릿(Action)들이 마켓플레이스에 많아 가져다 쓰기 편리합니다.
    

### 3. 어떻게 구성되어 있을까요? (기본 구조)

프로젝트 루트 디렉토리에 `.github/workflows/` 폴더를 만들고, 그 안에 `.yml` 확장자로 설정 파일을 작성하시면 됩니다. 대략적인 구조는 아래와 같습니다.

YAML

```
name: CI/CD Pipeline

on:
  push:
    branches: [ main ] # main 브랜치에 코드가 푸시될 때 작동합니다.

jobs:
  build-and-test:
    runs-on: ubuntu-latest # 최신 우분투 가상 환경에서 실행합니다.
    steps:
      - name: 1. GitHub 코드 가져오기
        uses: actions/checkout@v4

      - name: 2. 자바(Java) 환경 설정
        uses: actions/setup-java@v4
        with:
          distribution: 'temurin'
          java-version: '17'

      - name: 3. 빌드 및 테스트 실행
        run: ./gradlew build
```

_코드가 `main` 브랜치에 푸시되는 순간, GitHub가 우분투 환경을 켜서 자바 17을 설치하고 `./gradlew build` 명령어를 알아서 실행해 주는 방식입니다._
