## 1. 개요: Git 브랜치 전략이란?

여러 개발자가 함께 작업할 때, 마음대로 브랜치를 생성하고 합치면 코드가 엉키고 추적이 어려워집니다. Git 브랜치 전략(Branching Strategy)은 팀원들이 소스 코드를 깔끔하고 안정적으로 관리하기 위해 약속하는 **협업 규칙 및 프로세스**입니다.

## 2. GitFlow 전략

프로젝트를 안정적으로 관리하기 위해 **총 5가지 종류의 브랜치**를 운영하는 대규모 프로젝트용 전략입니다.

### 5가지 핵심 브랜치 역할

1. **`main` (또는 `master`)**
    
    - **역할:** 실제 유저에게 배포된(운영 중인) 완성된 코드가 존재하는 브랜치입니다.
        
2. **`develop`**
    
    - **역할:** 다음 버전을 위한 신기능 개발을 통합하고 진행하는 메인 개발 브랜치입니다.
        
3. **`feature`**
    
    - **역할:** 특정 기능(예: `feature/길드`, `feature/친구`)을 만드는 임시 브랜치입니다.
        
    - **흐름:** `develop`에서 따와서 개발한 뒤, 테스트가 완료되면 다시 `develop`으로 합칩니다.
        
4. **`release`**
    
    - **역할:** 정식 출시 전, 마지막 QA(품질 검사) 및 버그 수정을 진행하는 임시 브랜치입니다.
        
    - **흐름:** `develop`에서 생성해 테스트 및 최종 점검을 마친 뒤 `main`과 `develop` 양쪽에 합칩니다.
        
5. **`hotfix`**
    
    - **역할:** 배포된 `main` 버전에서 치명적인 버그(예: 골드 복사 버그)가 터졌을 때 긴급하게 수정하는 브랜치입니다.
        
    - **흐름:** `main`에서 직접 따서 신속하게 수정한 후, `main`과 `develop`에 즉시 반영합니다.
        

- **장점:** 배포 버전 관리가 명확하며, 신입 개발자나 대규모 팀이 작업해도 기존 서비스 코드가 훼손될 위험이 낮고 안정적입니다.
    
- **단점:** 브랜치 구조가 복잡하여 빠른 배포 및 지속적 전달(CD) 구조에는 부적합할 수 있습니다.
    

## 3. Trunk-based (트렁크 베이스드) 전략

복잡한 브랜치 구조를 배제하고, 빠른 개발과 배포에 집중하기 위한 현대적 전략입니다.

- **운영 방식:**
    
    1. 여러 메인 브랜치를 두지 않고, 중앙의 단일 **`main` 브랜치 하나만 운영**합니다.
        
    2. 작업(기능 구현/버그 수정)이 필요할 때 `main`에서 아주 수명이 짧은 브랜치를 짧게 따서 작업한 뒤 즉시 `main`으로 합칩니다.
        
    3. `main`에 코드가 합쳐지면 즉시 유저에게 배포합니다.
        
- **장점:** 관리할 브랜치가 적어 복잡도가 낮고 빠르게 개발할 수 있습니다. (비슷한 개념으로 **GitHub Flow** 전략도 있습니다)
    
- **전제 조건:** 코드가 검증 없이 곧바로 배포되기 때문에, 강력한 자동화 테스트(CI)와 **자동 배포(CD) 시스템**이 반드시 구축되어 있어야 합니다.
    

## 💡 학부생 프로젝트 적용 팁

학부생 개인/팀 프로젝트나 방학 스터디에서는 보통 **Trunk-based**나 조금 더 간소화된 **GitHub Flow** (Main + Feature 브랜치만 운영) 방식이 적합합니다. 브랜치 전략을 먼저 설정한 후, PR(Pull Request) 시 **GitHub Actions**로 테스트가 자동 실행되도록 연결하면 아주 훌륭한 포트폴리오 스펙이 될 수 있습니다.

### 1. 영상 도입부: 브랜치 전략이 필요한 이유

- **문제 상황:** 단순히 Git에서 브랜치를 만들고 Merge하는 법만 배웠다고 해서 10~20명의 개발자가 각자 마음대로 브랜치를 만들고 합치면, 개발 과정이 매우 복잡해지고 누군가 무슨 작업을 했는지 추적이 불가능해집니다.
    
- **해결책:** 여러 명의 개발자가 함께 작업을 깔끔하고 매끄럽게 진행하기 위해 도입하는 협업 방법론(전략)이 필수적입니다.
    
- **팀장 라이프:** 팀장으로서 팀을 이끌고 싶다면 이러한 전략을 꼭 알아야 하며, 평생 코딩만 할 게 아니라면 잘 알아두는 것이 좋습니다 (영상 특유의 유머).
    

### 2. GitFlow 전략 (예시 중심의 상세 흐름)

영상에서는 이해를 돕기 위해 "던전앤파이터 M"이라는 게임 개발 팀장이 된 상황을 예시로 듭니다.

- **배경 예시:** 기존 0.9 버전까지는 주먹구구식으로 개발했지만, 1.0 버전부터는 신기능이 많아 제대로 개발 프로세스를 구축하고자 GitFlow를 도입합니다.
    
- **Main 브랜치:**
    
    - 기존 0.9버전 완성 코드가 들어있는 메인 저장소입니다.
        
    - 신입 개발자가 이 원본 코드를 건드려 사고치는 것을 막기 위해 직접 개발을 절대 금지합니다.
        
- **Develop 브랜치:**
    
    - 원본 코드를 사본으로 복제해 만든 브랜치로, 모든 신기능 개발이 합쳐지는 공간입니다.
        
- **Feature 브랜치:**
    
    - `Develop`에 바로 코드를 덮어씌우는 것도 위험하므로, 기능 단위로 개별 브랜치를 따서 작업합니다.
        
    - **예시:** `feature/길드` 브랜치(길드 기능 개발), `feature/프렌드` 브랜치(친구 기능 개발).
        
    - 완성이 확인되면 `Develop` 브랜치로 합칩니다.
        
- **Release 브랜치:**
    
    - `Develop`의 코드가 어느 정도 완성되어 정식 출시 직전 단계에 만드는 임시 브랜치입니다.
        
    - 여기서 최종 테스트, QA, 소소한 고침 작업을 진행한 뒤 `Main`으로 합쳐 유저에게 배포합니다.
        
    - **실무 비하인드:** 사실 완벽히 완성되어 출시하기보다는 **데드라인에 쫓겨서 출시**하는 경우가 많다고 언급합니다.
        
    - **중요 처리:** `Release`에서 고쳐진 변경 사항은 다음 개발을 이어가기 위해 반드시 `Develop` 브랜치에도 똑같이 머지(합침)해 주어야 합니다.
        
- **Hotfix 브랜치:**
    
    - 1.0 정식 출시 후 유저들이 **'골드 무한 복사'** 같은 치명적 버그를 발견했을 때 사용합니다.
        
    - `Develop`을 거치면 시간이 오래 걸리므로 `Main`에서 바로 긴급 브랜치를 따서 고친 후, 즉시 `Main`에 합쳐 유저들에게 재배포합니다.
        
    - **유머 요소:** 점검 업데이트 시 유저 달래기용으로 '데이터 쪼가리(보상)'를 줘서 조련한다는 드립이 포함되어 있습니다.
        

### 3. GitFlow의 한계 및 주의사항

- **한계:** 정석대로 따라 할 필요는 없으며, 최근 유행하는 Continuous Delivery(지속적 전달) 같은 방식에는 GitFlow가 너무 무겁고 적합하지 않을 수 있습니다.
    
- **팀장의 책임:** 필요 없는 브랜치(예: Release 브랜치)는 프로젝트 상황에 맞게 쳐내고 변형해서 써야 하며, 팀장은 그 선택에 대한 합당한 근거를 대야 합니다. (책임은 밑 직원에게 전가하면 된다는 농담도 덧붙입니다.)
    

### 4. Trunk-based / GitHub Flow 전략

GitFlow의 복잡함을 해결하기 위한 대안으로 언급됩니다.

- **운영 방식:** `Develop` 같은 여러 브랜치를 두지 않고, 오직 **`Main` 브랜치 하나만 운영**합니다.
    
- **흐름:** 기능 개발이나 버그 수정이 필요하면 `Main`에서 잠깐 브랜치를 만들었다가 코드를 짜고 즉시 `Main`으로 합친 뒤, 그대로 유저에게 배포합니다.
    
- **GitHub Flow:** Trunk-based와 매우 유사한 전략으로 소개됩니다.
    
- **장점:** 여러 개의 소스 코드 브랜치를 유지·관리할 필요가 없습니다.
    
- **핵심 전제조건:** `Main`에 합쳐지자마자 바로 유저에게 넘어가기 때문에, 수많은 자동화 테스트(CI)와 **배포 자동화(CD) 시스템** 구축이 필수로 뒷받침되어야 합니다.
    
- **적합한 프로젝트:** 코드 수정량이 많지 않고, 이미 서비스 구조가 많이 안정화된 프로젝트에 도입하면 효과적입니다.
