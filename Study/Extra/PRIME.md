# ==디버깅 방법==


**VSCode 디버거 (추천)**: 확인하고 싶은 줄 왼쪽 여백을 클릭하면 빨간 점(브레이크포인트)이 생기고, `F5`로 디버그 실행하면 **그 줄에서 실행이 멈춥니다.** 그 상태에서:

- 왼쪽 "Variables" 패널에 그 시점의 모든 변수 값이 실시간으로 보임
- 아래 "Debug Console"에 `matrix.shape`, `mean[0]` 같은 걸 직접 타이핑해서 즉석으로 물어볼 수도 있음

**`breakpoint()` 내장함수**: 코드 중간에 그냥 `breakpoint()` 한 줄만 넣고 터미널에서 평범하게 실행하면, 그 줄에서 멈추고 파이썬 대화형 디버거(pdb)로 들어갑니다. 거기서 `matrix.shape`, `mean` 등 아무 변수나 쳐서 바로 확인 가능하고, `c`(continue) 치면 계속 진행됩니다. VSCode 없이 터미널만으로 할 수 있는 방법이에요.


## 사용법

1. **`training/train_router.py`(원본, 사본 아님! : 실행가능한 파일이어야 함.)를 열고**, 확인하고 싶은 줄 왼쪽 여백을 클릭해서 브레이크포인트(빨간 점)를 찍습니다. 예를 들어 `matrix, targets = build_training_matrix(...)` 다음 줄에요.
2. 왼쪽 사이드바에서 "Run and Debug" 아이콘(벌레+삼각형) 클릭 → 위쪽 드롭다운에서 `train_router.py (실제 인자로)` 선택 → **F5**.
3. 정상적으로 실행되다가 브레이크포인트에서 딱 멈춥니다. 그 시점의 모든 변수가 "Variables" 패널에 보이고요.

**여기서 님이 원하시던 "직접 타이핑"이 됩니다** — 화면 아래 **"Debug Console"** 탭에 `matrix.shape`, `mean[0]`, `type(episode)` 같은 걸 그냥 쳐서 엔터 치면, **그 순간 멈춰있는 진짜 프로그램 상태**를 가지고 즉석으로 답해줍니다. `print`를 코드에 미리 박아둘 필요 없이, 멈춘 자리에서 궁금한 걸 그때그때 물어볼 수 있는 거예요.

(`.vscode/`는 `.gitignore`에 이미 걸려있어서 이 설정 파일은 순수 로컬 전용입니다 — 커밋될 걱정 없어요.)

## 제가 실제로 돌려본 방법 — 그대로 따라 하실 수 있습니다

지금까지 제가 "실제로 돌려보면" 하고 보여드린 건 전부 이 패턴입니다:

```bash
cd "SmartRouter-main 폴더"
py -3.13 -c "
import sys
sys.path.insert(0, 'src')          # 우리 패키지(ossp_router) 찾을 수 있게 경로 추가
from ossp_router.protocol import load_input
from pathlib import Path

inputs = load_input(Path('data/toy/inputs.json'))   # 진짜 데이터 로드
print(inputs.episodes[0], '\n')                             # 확인하고 싶은 거 print
"
```

**핵심은 `py -3.13 -c "..."`** — 따옴표 안에 파이썬 코드를 통째로 넣으면, 터미널이 그걸 **그 자리에서 바로 실행하고 결과를 보여줍니다.** 

진짜 파일을 하나도 안 건드리고, 실행 끝나면 흔적도 안 남아서, "이 함수 진짜 이렇게 동작하나?" 싶을 때마다 던져보기 딱 좋습니다.

# 무결성 보장, error 처리 단위

**처음부터 이걸 완벽하게 감 잡는 사람은 전 세계에 없습니다.** 선배들이 짜놓은 코드나 유명 오픈소스를 보면서 **"아, 이 시점에는 이런 실수가 자주 나니까 이걸 걸어두는구나"** 하고 하나씩 체득해 나가는 거죠.

현업에서 `assert`나 무결성 검증 코드를 어디에 배치해야 할지 감을 잡는 **실전 팁 4가지**를 정리해 드립니다.

### 1. "외부에서 데이터가 들어오는 입구" (Boundary)

- **언제:** 함수나 API의 파라미터로 데이터가 처음 들어올 때, 혹은 파일/DB에서 데이터를 읽어올 때입니다.
    
- **이유:** 함수 안쪽으로 들어가서 에러가 나면 원인을 찾기 어렵습니다. 아예 문지기(`assert`)를 세워두고 "입력 데이터의 형태(Shape)가 왜 이 모양이야?" 하고 입구에서 바로 차단하는 것입니다.
    
- **예시:** `assert matrix.ndim == 2`, `assert len(matrix) == len(targets)`
    

### 2. "내 가정이 확실한 곳" (Sanity Check / 상식 검증)

- **언제:** 코드를 짜다 보면 내 머릿속에서 "여기서는 당연히 두 데이터의 평균이 같아야 해!"라는 수학적/논리적 전제가 생기는 순간이 있습니다.
    
- **이유:** 내 논리는 맞았겠지만, 미래의 나나 다른 팀원이 코드를 수정하면서 이 전제를 깨버릴 수 있습니다. 이때 "내 생각이 맞는지 컴퓨터한테 강제로 확인시키는 용도"로 `assert`를 심어둡니다. (방금 보신 `score_mean`과 `cost_mean` 비교가 딱 이 케이스입니다.)
    

### 3. "치명적인 버그로 이어질 수 있는 위험한 연산 직전"

- **언제:** 0으로 나누기(`ZeroDivisionError`), 잘못된 차원끼리의 행렬 곱셈(`MatMul Error`), 빈 배열에 대한 연산 등 **터지면 앱이 죽거나 엉뚱한 값이 조용히 만들어지는 위험한 구간**입니다.
    
- **이유:** 파이썬은 멍청하게도 엉뚱한 계산 결과를 조용히 뱉고 넘어갈 때가 있는데(Silent Failure), 이게 제일 무섭습니다. `assert`를 통해 "여기 값 0 아니지?" 하고 단단히 묶어두는 것입니다.
    

### 4. 실전에서 쓰는 마인드셋: "미래의 나를 못 믿는다"고 생각하기

- 주니어 시절에는 "내가 코드를 잘 짜면 되지"라고 생각하지만, 시니어들은 "내 코드는 언젠가 망가진다. 그리고 나중에 야근할 때 범인을 찾으려면 컴퓨터가 직접 에러를 뱉어줘야 한다"고 생각합니다.
    
- 그래서 찝찝한 부분이 있다면 과감하게 `assert`를 적어두거나 예외 처리를 해둡니다. 에러 메시지가 친절하게 나올수록 디버깅 시간이 획기적으로 줄어들거든요.
