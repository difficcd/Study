  - 정확히는 SSD 안에 파티션(구획)을 만들고 거기에 시스템 파일이 들어갑니다. 리눅스는 /(루트)라는 곳에 깔려요 — Windows의 C:\에 해당.

  8. OS 바꾸면 F:는 안전한가?

  - 리눅스 설치 화면에서 "디스크 전체 지우고 설치"를 무심코 누르면 위험하니, 수동 파티션에서 Disk 0(120GB SSD)만 선택하는 게 핵심.
  - F:는 NTFS 포맷이라 리눅스에서도 읽고 쓸 수 있어요. draw 폴더, 카톡 받은 파일 등 그대로 사용 가능.
  - ⭐ 그래서 백업 이미지도 F:에 저장하는 거고, 만약 F:에 백업 두고 F:를 실수로 밀면 백업까지 날아가니 — 정말 중요한 건 외장하드나 USB에 한 번 더 두는 게 안전.

# 복구 드라이버 원리

### 복구 드라이브가 하는 일

"복구 드라이브 만들기"는 크게 두 가지를 USB에 담습니다.

1. **윈도우 복구 환경(WinRE)** — 윈도우가 정상 부팅이 안 될 때 띄울 수 있는 최소한의 "응급실" 환경. 시작 복구, 시스템 복원, 명령 프롬프트, 이전 버전으로 되돌리기 같은 도구들이 여기 들어있어요.
2. **(체크박스 선택 시) 시스템 파일 백업** — 지금 C: 드라이브에 있는 윈도우 설치 파일 자체를 통째로 복사해둡니다. 이 옵션을 켜면 USB만 있으면 **아예 처음부터 다시 윈도우를 설치할 수 있는 매체**가 돼요 (재설치 미디어 역할까지 겸함).

즉 이 USB는 "지금 이 순간의 윈도우 상태를 재현할 수 있는 응급 키트"라고 보면 됩니다.

### 이게 왜 이번 작업(Arch 설치)에 안전장치가 되냐면

만약 나중에 실수로 (거의 그럴 일 없게 설계했지만) 디스크 0의 부트 정보가 꼬이는 상황이 생기면:

- 이 USB로 부팅 → **"문제 해결" → "시작 복구"** 실행 → 윈도우 부트로더/MBR 부트코드를 원래대로 복구 (= 자동으로 문제 해결함. 대부분의 문제가 여기서 해결 가능)
- 그래도 안 되면 → 시스템 파일 백업이 되어 있으니 최악의 경우 **윈도우 자체를 이 USB로 재설치** 가능 (윈도우 설치 이미지로 처음부터 다시 윈도우 설치)

지금 계획대로 GRUB을 디스크 1에만 설치할 거라 이 USB를 실제로 쓸 일은 거의 없을 가능성이 높아요. 그냥 "혹시 몰라서" 준비해두는 보험 개념입니다.

### 만들 때 체크할 것

- "시스템 파일을 복구 드라이브에 백업" 체크박스는 **켜두세요** (용량은 더 필요하지만 — USB에 있는 다른 파일은 삭제되니 빈 USB 쓰세요 — 재설치 미디어 기능까지 얻는 게 훨씬 유용함)
- 완료되면 USB 안 쓰는 서랍 같은 데 넣어두고, **컴퓨터에 문제 생겼을 때만** 꺼내서 부팅용으로 쓰면 됩니다



@ **시작 복구는 딱 윈도우 부팅에 필요한 범위(C: 드라이브 + 부트코드/BCD)만 건드립니다.** F: 드라이브(디스크 1)는 아예 손도 안 대요.



#  CND (Content Delivery Network)

### 원리

전 세계 곳곳에 **똑같은 콘텐츠(웹사이트 이미지, 동영상, 파일 등)의 복사본을 여러 서버에 미리 뿌려두고**, 사용자가 접속하면 지리적으로 가장 가까운(또는 가장 빠른 경로의) 서버에서 응답을 주는 시스템이에요.

- 예: 유튜브 영상을 한국에서 볼 때, 실제 원본 서버는 미국에 있어도 한국이나 아시아 근처에 있는 CDN 서버가 그 영상 복사본을 캐싱해두고 있다가 그쪽에서 바로 전송해줘요.
- 그래서 물리적 거리가 줄어들고, 중간 경유 구간(홉)도 적어져서 **로딩이 빠르고 지연(latency)이 낮아짐**.
- 넷플릭스, 유튜브, 대부분의 큰 웹사이트가 CDN을 씁니다 (Cloudflare, Akamai, CloudFront 등이 유명한 CDN 업체).

### 미러 서버와의 공통점/차이점

- **공통점**: "가까운 곳에서 받으면 빠르다"는 원리는 완전히 같아요.
- **차이점**:
    - CDN은 보통 **상업적 업체가 자동으로 관리**하면서, 어떤 서버가 제일 가까운지 자동 라우팅까지 해줘요 (사용자가 서버를 고를 필요 없음, 알아서 최적 경로로 감).
    - 미러는 **여러 독립 기관이 자발적으로 파일을 복사**해두고, 사용자가 리스트에서 **직접 골라서** 접속하는 방식이에요 (자동 라우팅이 없거나 약함).

즉 개념은 같은데, CDN은 "자동화되고 상업적인 버전", 미러는 "수동으로 고르는, 커뮤니티 기반 버전"이라고 보면 됩니다.


# 미러 서버

### 미러 서버 = 맞아요, 그 예상이 정확해요

- Arch 같은 오픈소스 프로젝트는 전 세계 대학, 호스팅 업체, 자원봉사 단체들이 **똑같은 파일을 자기 서버에 복사해서 무료로 배포**해줘요. 이걸 "미러(mirror)"라고 부릅니다.
- 원리는 CDN이랑 비슷해요: 물리적으로 가까운 서버에서 받을수록 **네트워크 지연(latency)이 짧고, 해당 지역 회선 대역폭도 더 잘 나와서** 다운로드가 빨라져요.
- 한국(카이스트 등)에서 받으면 미국/유럽 서버에서 받는 것보다 훨씬 빠른 게 보통이고, 특히 ISO처럼 1GB급 파일은 이 차이가 체감이 커요.
- 내용물 자체는 전 세계 어느 미러든 **100% 동일**합니다. "느린 길 vs 빠른 길"의 차이일 뿐이에요.

### ISO의 원리

"OS를 압축해서 가져오는 것"이라기보다는, **CD/DVD 한 장의 내용을 통째로 그대로 떠낸 파일**이라고 보는 게 정확해요.

- ISO 안에는 부팅 가능한 작은 리눅스 환경이 통째로 들어있어요: 커널, 최소한의 파일시스템, 설치 도구들.
- USB로 부팅하면 이 안의 내용이 **RAM 위에 그대로 올라와서 "라이브 환경"**이 돼요 — 디스크에 아무것도 설치 안 된 상태에서 임시로 작동하는 미니 OS인 셈이죠. (우분투 라이브 USB랑 같은 개념)
- 그 안에서 실제로는 대부분 **squashfs**라는 읽기 전용 압축 파일시스템으로 패키지들이 눌러 담겨 있어서, 실제 설치될 내용물보다 ISO 자체 용량은 꽤 줄어든 상태예요. 예를 들어 설치되면 몇 GB가 될 시스템이 ISO 안에서는 압축돼서 1GB 남짓으로 들어있는 거고요.
- 부팅하고 나서 필요한 순간에 이 압축된 걸 풀어서 디스크에 실제로 써넣는 게 "설치" 과정입니다.

정리하면: **ISO = "CD 한 장 분량의, 부팅 가능한 압축 리눅스 이미지"**이고, 이게 USB에 구워지면 그 USB가 임시로 부팅 가능한 미니 컴퓨터처럼 동작하는 거예요.


# 파일 다운로드 (부속..)

### 파일 다운로드 경로

말씀하신 흐름이 맞아요, 조금 더 정확하게 그리면:

```
내 컴퓨터 (브라우저/Rufus 등)
  → 이더넷/와이파이 (집 안 네트워크)
  → 공유기(라우터) - NAT 처리, 사설IP↔공유기 사이 라우팅
  → ISP(인터넷 서비스 제공자) 망
  → 인터넷 backbone (여러 라우터 홉을 거침)
  → 목적지 서버(cicku.me 같은 미러 서버)가 있는 데이터센터
  → 그 서버가 파일을 응답으로 전송
  → 역순으로 내 컴퓨터까지 돌아옴
```

이 과정이 **TCP/IP** 위에서 이뤄지고, 그 위에 **HTTP**라는 프로토콜이 얹혀서 "이 파일 주세요"라는 요청과 응답을 주고받아요.

### GET / fetch 관련

- **GET**: HTTP 요청 메소드 중 하나예요. "서버야, 이 URL에 있는 자원(파일이든 페이지든)을 다오"라는 뜻. 웹사이트 열람, 파일 다운로드 링크 클릭 대부분이 내부적으로 GET 요청이에요. (반대로 POST는 "이 데이터를 서버에 보낸다/저장해줘"에 가까움)
- **fetch**: 이건 프로토콜이 아니라 **자바스크립트에서 HTTP 요청을 보내는 함수(API)**예요. 웹페이지 안에서 코드로 "서버한테 GET/POST 요청 보내줘"라고 할 때 쓰는 도구입니다. 즉 GET은 "요청의 종류", fetch는 "그 요청을 코드로 실행하는 방법" — 계층이 달라요.

그래서 브라우저에서 ISO 다운로드 링크를 클릭하면: 브라우저가 그 URL로 **HTTP GET 요청**을 보내고 → 미러 서버가 파일 데이터를 여러 개의 패킷으로 쪼개서 응답 → 내 컴퓨터가 그 패킷들을 순서대로 재조립해서 로컬 디스크에 `archlinux-x86_64.iso`로 저장하는 거예요.


# HTTPS, HTTP

HTTP와 HTTPS의 차이는 딱 하나예요 — **암호화 여부**입니다.

### 핵심 차이

- **HTTP**: 클라이언트(내 컴퓨터)와 서버가 주고받는 데이터가 **평문(암호화 안 됨)** 으로 오갑니다.
- **HTTPS**: 똑같은 HTTP인데, 그 위에 **TLS(예전엔 SSL)라는 암호화 계층**을 씌운 거예요. `HTTP + TLS = HTTPS`

### 왜 문제가 되냐면

HTTP로 통신하면, 아까 말한 경로(공유기 → ISP → 인터넷 백본 → 목적지 서버) **중간의 어느 지점에서든 누군가 패킷을 들여다보면 내용이 그대로 읽힙니다.**

- 카페 와이파이 같은 공용 네트워크에서 누가 스니핑(패킷 가로채기)하면 로그인 비밀번호, 카드번호 같은 게 그대로 노출될 수 있음
- 중간에서 내용을 바꿔치기(변조)하는 것도 가능 (예: 다운로드 파일에 악성코드 끼워넣기)

HTTPS는 TLS 핸드셰이크로 **암호화 키를 안전하게 교환**한 다음, 그 이후 모든 데이터를 암호화해서 주고받기 때문에 중간에서 가로채도 내용이 뒤죽박죽(암호문)으로만 보여요. 서버가 진짜 그 서버가 맞는지 **인증서로 신원도 검증**하고요.

### 방금 하신 ISO 다운로드랑 연결하면

- ISO 자체는 어차피 공개 파일이라 "내용을 숨겨야 할 이유"는 없지만, **무결성(변조 안 됐는지)** 측면에서 HTTPS가 중요해요.
- HTTP로 받으면 중간에서 이론상 ISO 파일에 악성코드를 끼워넣고 바꿔치기하는 공격(MITM)이 가능하지만, HTTPS면 그게 막혀요.
- 그래서 미러 사이트 주소가 `https://`로 시작하는지 한 번 확인해보시면 좋아요 — 요즘은 거의 다 기본으로 HTTPS 지원합니다.

---

### 로컬 개발(localhost) = 사실상 네트워크에 안 나갑니다

Vite로 `localhost:5173` 같은 데 접속해서 개발할 때, 이건 **`127.0.0.1`(loopback, 루프백)** 이라는 특수 주소로 접속하는 거예요. 이 요청은:

- 이더넷 카드나 와이파이 안테나를 거치지 않고, **컴퓨터 내부에서 커널이 자체적으로 처리**합니다.
- 즉 공유기, ISP, 인터넷 어디에도 안 나가요 — **패킷이 물리적으로 컴퓨터 밖으로 나간 적이 없으니 가로챌 방법 자체가 없습니다.**
- 그래서 `localhost`로만 접속해서 개발하는 동안은 HTTP든 뭐든 상관없이 **완전히 안전**해요.

### 그런데 노트북/휴대폰 등 다른 기기에서 같은 앱에 접속하면 얘기가 달라져요

`vite --host` 옵션으로 `0.0.0.0`에 바인딩해서 **같은 와이파이의 다른 기기(휴대폰 등)에서 `192.168.x.x:5173`으로 접속**하는 상황이면, 이제 진짜로 **공유기(로컬 네트워크)를 거칩니다.**

- 이 경우 **같은 와이파이에 붙어있는 다른 사람/기기**가 이론적으로 패킷을 스니핑할 수 있어요 (와이파이 자체 암호화(WPA2/3)가 있긴 하지만, 같은 네트워크 안의 기기끼리는 여러 우회 기법으로 서로 트래픽을 볼 수 있는 경우가 있음)
- 그래서 "로컬이니까 무조건 안전"이 아니라, **정확히는 loopback(127.0.0.1)만 안전하고, 네트워크 인터페이스에 바인딩되는 순간부터는 진짜 네트워크 보안 문제**가 됩니다.

### "배포된 서버에서만 채갈 수 있다"는 건 정확한 이해가 아니에요

핵심은 "배포됐냐 아니냐"가 아니라 **"트래픽이 공유되는/신뢰할 수 없는 네트워크 구간을 실제로 지나가느냐"** 예요.

- Loopback(자기 자신) → 아무도 못 가로챔
- 집 공유기 안(로컬 LAN) → 같은 네트워크에 있는 사람만 이론상 가능
- 인터넷을 통해 배포된 서버 → 훨씬 더 많은 중간 구간(ISP, 백본 라우터 등)을 지나가니 **가로챌 수 있는 지점(공격 표면)이 훨씬 많아짐**

즉 배포 서버가 특별히 더 위험한 게 아니라, **거치는 구간이 많아질수록 위험 지점도 늘어나는 것**뿐이에요.

### IP / MAC 주소를 채갈 수 있냐

이 둘은 완전히 다른 성격이에요.

- **IP 주소**: HTTPS로 암호화해도 **IP 헤더 자체는 암호화 대상이 아니에요.** 라우팅을 하려면 중간의 모든 라우터가 "어디로 보내야 하는지" 알아야 하니까, 출발지/목적지 IP는 원래 평문으로 노출됩니다. (암호화되는 건 HTTP body/내용물이지, 패킷 껍데기인 IP 헤더가 아니에요) 그래서 IP는 HTTP든 HTTPS든 상관없이 애초에 숨겨지는 정보가 아니에요.

- **MAC 주소**: 이건 좀 달라요. MAC 주소는 **같은 로컬 네트워크 구간(같은 스위치/와이파이 AP)에서만 의미가 있는 주소**입니다. 패킷이 공유기(라우터)를 한 번 거치면, 그다음 구간부터는 **MAC 주소가 라우터의 것으로 바뀌어서 나가요** (이걸 캡슐화/재작성이라고 봐도 돼요). 그래서:
    - 인터넷 건너편의 누군가가 내 MAC 주소를 직접 알아낼 방법은 사실상 없어요 (첫 홉을 넘어가면 이미 사라진 정보라서)
    - 하지만 **같은 공유기/와이파이에 붙어있는 사람**은 ARP 같은 걸로 내 기기 MAC 주소를 볼 수 있어요

### 정리

- `localhost`로만 개발 중이면: 안전 (네트워크에 아예 안 나감)
- `0.0.0.0` + LAN으로 열어두면: 같은 와이파이 안에서는 이론상 위험 존재 → 이때부터 HTTPS 여부가 의미 생김
- IP는 원래 숨길 수 없는 정보 (라우팅 필수 정보)
- MAC은 로컬 네트워크 안에서만 노출, 인터넷 건너편에서는 안 보임



# 보안 관련 (1)

### 1. 정보를 "채가는" 방식 — 패킷 스니핑

네트워크에서 데이터는 **패킷**이라는 작은 단위로 쪼개져서 전송돼요. 
이 패킷이 지나가는 경로 어딘가에서 "옆에서 엿듣는" 게 스니핑이에요.

원리는 생각보다 단순해요. 와이파이를 예로 들면, 와이파이는 본질적으로 **공기 중에 전파(radio)를 뿌리는 방식**이라 같은 AP(공유기)에 붙어있는 기기들은 물리적으로 모든 전파를 수신할 수 있어요. 보통은 "내 것이 아닌 패킷"은 네트워크 카드가 무시하는데, **프로미스큐어스 모드(promiscuous mode)** 라는 걸 켜면 지나가는 모든 패킷을 다 잡아서 읽을 수 있게 돼요. 이걸 할 수 있는 도구가 예를 들면 **Wireshark** 같은 패킷 분석 프로그램이에요.

유선(이더넷)도 비슷한데, 옛날 허브(hub) 환경에서는 모든 포트에 모든 패킷이 브로드캐스트돼서 아무나 다 볼 수 있었어요. 요즘 스위치(switch, 네트워크수업 rv ; 기반 환경에서는 해당 포트로만 패킷이 가니까 직접 스니핑이 어렵지만, **ARP 스푸핑** 같은 기법으로 "나한테도 패킷 보내줘"라고 속이는 공격이 가능해요.

그래서 HTTPS가 중요한 게, 패킷을 가로채도 **내용물이 암호화되어 있으면 읽을 수 없어서** 방어가 되는 거예요.

### 2. 정보이론 수업에서 이걸 배우나?

아마 기대하시는 내용과는 다를 거예요. "정보이론(Information Theory)"은 보통 **샤논(Shannon)의 엔트로피, 채널 용량, 압축 한계** 같은 수학적/확률적 이론을 다뤄요. "정보를 어떻게 효율적으로 전송/압축할 수 있는가"에 대한 수학이지, 해킹/보안/스니핑을 직접 다루진 않아요.

지금 궁금해하시는 내용은:

- **컴퓨터 네트워크** 과목 — TCP/IP 계층, 라우팅, 패킷 구조
- **정보보호/네트워크 보안** 과목 — 스니핑, 암호화, TLS, 공격 기법

이 두 과목에서 배우게 될 거예요.

### 3. 공유기에서 검색기록/유저 정보 조회 가능한가?

공유기마다 다른데, 대부분의 가정용 공유기에서 볼 수 있는 건:

- **현재 접속 중인 기기 목록**: IP 주소, MAC 주소, 기기 이름 → 거의 모든 공유기에서 볼 수 있어요
- **DHCP 할당 내역**: 어떤 MAC 주소에 어떤 IP를 언제 줬는지 → 대부분 가능
- **DNS 쿼리 로그(= 어떤 도메인에 접속 시도했는지)**: 이건 공유기 종류에 따라 다릅니다. 고급 공유기(예: ASUS 등)는 로그를 남기기도 하지만, 저가 공유기는 저장 용량이 부족해서 안 남기는 경우가 많아요

중요한 건, **검색 내용 자체**(예: 구글에서 뭘 검색했는지, 페이지 안에서 뭘 봤는지)는 공유기에서 볼 수 없어요. 왜냐하면 요즘 거의 모든 사이트가 HTTPS를 쓰니까, 공유기가 볼 수 있는 건 **"이 기기가 google.com에 접속했다"** 정도이지, **"google.com에서 뭘 검색했는지"** 는 TLS로 암호화돼서 안 보여요.

정리하면: 공유기 관리자 페이지(`192.168.0.1` 등)에서 접속된 기기들의 IP/MAC은 바로 볼 수 있고, 어떤 "도메인"에 접속했는지까지는 설정에 따라 가능하지만, 암호화된 내용물(검색어, 입력한 비밀번호 등)은 못 봅니다.

# 보안 관련 (2)

### 같은 네트워크에서 트래픽을 보는 방법

프로미스큐어스 모드는 그 중 하나인데, 그것만으로는 부족한 경우가 많아요. 주요 기법을 설명하면:

#### 와이파이 환경

프로미스큐어스 모드(+ 모니터 모드)를 켜면 **공기 중에 날아다니는 전파를 다 수신**할 수 있어요. 다만 WPA2/WPA3로 암호화된 와이파이에서는 각 기기마다 세션 키가 다르게 생성되기 때문에, 같은 비밀번호를 알아도 다른 기기의 패킷을 바로 복호화하기는 쉽지 않아요. 

하지만 **핸드셰이크(접속 과정)를 캡처**하면 세션 키를 유도해서 풀어볼 수 있는 경우가 있고, 특히 WPA2-PSK(가정용) 환경에서는 비밀번호만 알면 이론상 가능해요.

#### 유선(스위치) 환경 — ARP 스푸핑

요즘 << 유선 환경은 스위치가 "이 MAC 주소는 이 포트로"라고 구분해서 보내주니까 >> (스위치 = 멀티포트 브릿지 , 브릿지 = 똑똑한 허브) , 
단순히 프로미스큐어스 모드를 켜도 남의 패킷이 내 포트로 안 와요. 그래서 쓰는 게 **ARP 스푸핑**인데, (ARP = 컴퓨터나 공유기가 네트워크 통신을 하기 위해 **IP 주소와 물리적 MAC 주소를 1:1로 연결해 저장하는 목록**) 
원리가 이래요: 

- 정상 상황: 기기 A가 공유기한테 보낼 때, ARP 테이블에 "공유기 IP = 공유기 MAC"이 기록되어 있어서 패킷이 공유기로 감
- 공격자 C가 네트워크에 "공유기 IP는 사실 내 MAC이야"라는 **가짜 ARP 응답을 계속 뿌림**
- 기기 A가 속아서 공유기한테 보낼 패킷을 **공격자 C한테 보내게 됨**
- 공격자 C는 그 내용을 엿본 다음 진짜 공유기로 전달해줘서 A는 정상 통신하는 것처럼 느낌

이게 전형적인 **중간자 공격(MITM)** 이에요. A 입장에서는 인터넷이 정상 작동하니까 당하고 있는지 모르고, C는 모든 트래픽을 엿볼 수 있게 되는 거죠. HTTP면 내용까지 다 보이고, HTTPS면 암호화되어 있어서 "어디에 접속하는지"만 보이고 내용은 못 봐요.

=>
### ARP가 원래 작동하는 방식

ARP는 놀라울 정도로 **순진한 프로토콜**이에요:

1. 기기 A가 "공유기 IP(192.168.0.1)의 MAC 주소가 뭐야?" 하고 네트워크에 **브로드캐스트** 질문을 던짐
2. 공유기가 "그거 나야, 내 MAC은 AA:BB:CC:DD:EE:FF야" 하고 응답
3. 기기 A가 이걸 **ARP 테이블**에 저장해두고, 이후 통신할 때 이 MAC 주소로 보냄

여기서 핵심적인 취약점이 뭐냐면, **ARP에는 인증이 전혀 없어요.** "너 진짜 공유기 맞아?"라고 확인하는 절차가 아예 없고, 누가 대답하든 그냥 믿습니다. 심지어 **물어보지도 않았는데 일방적으로 보내는 ARP 응답(Gratuitous ARP)** 도 그대로 받아들여요.

- 국가 단위 해킹 그룹(북한의 라자루스 등)이 실제로 활동하고 있다는 건 여러 보안 업체/정부 보고서에서 확인된 사실이에요

- 애초에 개인정보를 **암호화 안 하고 평문으로 저장**해둔 경우가 적발되기도 하고
- 보안 투자에 예산을 안 쓰는 기업 문화도 원인 중 하나 — "사고 나면 벌금 내는 게 보안에 투자하는 것보다 싸다"는 계산을 하는 곳도 현실적으로 있어요

결론적으로는 해커가 똑똑해지는 것도 맞고, 방어 측이 허술한 것도 맞고, 내부 소행인 경우도 실제로 있어요. "한 가지 원인"이라기보다는 공격 수준은 올라가는데 방어 수준이 그만큼 못 따라가는 **격차 문제**에 가까워요.

# 데이터 사용하는 경우 유저의 DNS정보를 통신사 기지국이 조회 가능한 구조인가?

모바일 데이터(LTE/5G)로 접속하면 
**통신사가 어떤 도메인에 접속했는지는 볼 수 있어요.**

### 왜냐면

모바일 데이터 통신 경로를 보면:

```
내 폰
  → 기지국 (통신사 소유)
  → 통신사 코어 네트워크 (통신사 소유)
  → 인터넷
  → 목적지 서버
```

집에서 와이파이 쓸 때 공유기/ISP가 중간에 있듯이, 데이터 쓸 때는 **통신사 자체가 ISP 역할**을 해요. 트래픽이 통신사 네트워크를 물리적으로 통과하니까, 통신사 입장에서 볼 수 있는 건:

- **접속한 도메인(SNI/DNS 쿼리)**: HTTPS를 써도 TLS 핸드셰이크 초반에 **SNI(Server Name Indication)** 라는 필드에 도메인 이름이 평문으로 노출돼요. 즉 "이 유저가 youtube.com에 접속했다"는 보임
- **접속 시간, 데이터 양, IP 주소**: 당연히 다 보임
- **내용물(뭘 검색했는지, 뭘 봤는지)**: HTTPS면 암호화돼서 못 봄

정리하면 통신사는 **"언제, 어디에 접속했는지"는 알 수 있지만, "거기서 뭘 했는지"는 HTTPS 덕분에 못 보는** 구조예요.

### 그럼 도메인 노출도 막을 수 있나?

방법이 있긴 해요:

- **ECH (Encrypted Client Hello)**: SNI까지 암호화하는 TLS 확장 기능인데, 아직 모든 서버/브라우저가 지원하는 건 아니에요. 점차 확산 중
- **VPN**: 통신사 입장에서는 "이 유저가 VPN 서버에 접속했다"만 보이고, 그 안에서 어떤 도메인으로 갔는지는 VPN 터널 안에 암호화돼서 안 보여요. 대신 VPN 업체가 그 정보를 볼 수 있게 되니까, 결국 **"누구를 믿느냐"가 통신사에서 VPN 업체로 옮겨가는 것**뿐이에요
- **DoH/DoT (DNS over HTTPS/TLS)**: DNS 쿼리 자체를 암호화해서 통신사가 DNS 레벨에서 도메인을 못 보게 하는 건데, SNI는 여전히 노출되니까 완전한 해결책은 아니에요

### 통신사가 이 정보를 실제로 보관하나?

한국은 **통신비밀보호법**에 의해 통신사가 통신사실확인자료(누가 언제 어디에 접속했는지 등)를 **일정 기간 의무 보관**해야 해요. 수사기관이 법원 영장을 받아서 요청하면 이 기록을 제공할 수 있고요. 그래서 "통신사가 볼 수 있냐"를 넘어서 **"실제로 기록하고 보관하고 있다"**가 맞아요.




# 핸드셰이크 캡처는 어떻게 할까?

"핸드셰이크"라는 게 거창한 게 아니라, **기기가 와이파이 AP(공유기)에 접속하는 순간 주고받는 4개의 패킷**(4-way handshake)이에요. 이 과정에서 비밀번호를 기반으로 세션 키를 생성하는데, 이 4개 패킷이 **공기 중 전파로 날아가요.**

캡처 방법 자체는 놀랍도록 단순해요:

1. 노트북의 와이파이 카드를 **모니터 모드**로 전환 (일반 모드는 "내 AP에서 온 패킷만 수신"이지만, 모니터 모드는 "주변의 모든 와이파이 전파를 무차별 수신")
2. **Wireshark**나 **airodump-ng** 같은 도구를 켜고 대기
3. 누군가가 와이파이에 접속(또는 재접속)하는 순간 → 그 4개 패킷이 공기 중으로 날아옴 → 그걸 그대로 저장

공격자가 능동적으로 할 수도 있어요 — **deauth 공격**이라고, 특정 기기한테 "너 접속 끊겨"라는 가짜 프레임을 보내서 강제로 재접속하게 만들면, 그 재접속 과정에서 핸드셰이크가 다시 발생하니까 그걸 캡처하는 거예요.

캡처한 다음엔 **오프라인에서 비밀번호 후보를 대입**해서(brute force / dictionary attack) 맞는지 확인해요. 비밀번호가 "12345678" 같은 거면 몇 초 만에 뚫리고, 복잡하면 현실적으로 못 뚫어요. 그래서 와이파이 비밀번호를 복잡하게 설정하라는 게 이 때문이에요.


# VPN 원리는 뭘까? 

간단히 정리

### VPN = Virtual Private Network

이름 그대로 **"가상의 사설 네트워크"**예요. 핵심 원리는 **터널링(tunneling)**이라는 개념이에요.

### 원리 — 편지 비유로 먼저

일반 통신이 **엽서**라고 생각해보세요. 겉면에 보내는 사람/받는 사람 주소(IP)가 적혀있고, 내용도 그대로 보임(HTTP). HTTPS면 내용은 암호화됐지만 겉면 주소는 여전히 보여요.

VPN은 이 엽서를 **불투명한 봉투에 넣어서, 봉투 겉면에는 "VPN 서버 주소"만 적는 것**이에요:

```
[일반 통신]
내 폰 → (목적지: youtube.com) → 통신사 → 인터넷 → youtube.com
         통신사가 "youtube.com 가는구나" 다 보임

[VPN 사용]
내 폰 → (목적지: VPN 서버) → 통신사 → VPN 서버 → youtube.com
         통신사가 보이는 건 "VPN 서버에 뭔가 보내는구나"뿐
         봉투 안에 진짜 목적지(youtube.com)가 들어있지만
          암호화돼서 안 보임
```

### 기술적으로 뭘 하는 건가

1. **암호화된 터널 생성**: 내 기기와 VPN 서버 사이에 TLS/IPsec 등으로 암호화 채널을 만듦
2. **캡슐화(Encapsulation)**: 원래 패킷(목적지: youtube.com)을 통째로 암호화한 다음, 그걸 **새 패킷의 페이로드(짐칸)** 에 넣어요. 새 패킷의 헤더에는 목적지가 "VPN 서버"로만 적혀있음
3. **VPN 서버에서 까기**: VPN 서버가 받아서 바깥 껍데기를 벗기고 → 안에 있던 원래 패킷을 꺼내서 → 진짜 목적지(youtube.com)로 대신 보내줌
4. **응답도 역순**: youtube.com이 VPN 서버한테 응답 → VPN 서버가 다시 암호화해서 내 기기한테 보냄

### 그래서 뭐가 숨겨지냐면

|VPN 없이|VPN 사용|
|---|---|---|
|통신사/공유기가 보는 것|목적지 도메인, IP, 접속 시간|"VPN 서버에 접속 중"만 보임|
|목적지 서버가 보는 것|내 진짜 IP|VPN 서버의 IP (내 IP 숨겨짐)|
|VPN 업체가 보는 것|—|전부 다 볼 수 있음|

마지막 줄이 핵심이에요. VPN을 쓰면 통신사한테는 숨길 수 있지만, **그 신뢰가 VPN 업체로 이전되는 것**뿐이에요. "no-log policy(기록 안 남긴다)"라고 광고하는 VPN 업체들이 많은데, 실제로 그런지 외부에서 검증하기가 어렵다는 게 현실이에요.

### 지역 우회가 되는 이유

넷플릭스가 "이 유저 IP가 한국이네 → 한국 콘텐츠 보여주자"라고 판단하는데, VPN을 미국 서버로 연결하면 넷플릭스 입장에서는 **미국 IP에서 접속한 것처럼 보이니까** 미국 콘텐츠가 뜨는 거예요. 원리 자체는 이렇게 단순합니다.







# VPN 구현의 어려운 점

### 1. 터널 자체를 어떻게 안전하게 여냐

VPN 서버와 내 기기가 처음 연결할 때, 암호화 키를 교환해야 하잖아요. 그런데 이 키 교환 자체가 아직 암호화 안 된 네트워크 위에서 이뤄져야 해요. "암호화를 시작하기 위한 대화를 암호화 없이 해야 한다"는 닭과 달걀 문제가 있어서, 디피-헬만(Diffie-Hellman) 같은 키 교환 알고리즘이 필요해요. 이 부분의 설계가 허술하면 터널 자체가 뚫려요. 

### 2. 성능 문제

모든 패킷을 암호화 → 캡슐화 → 전송 → 복호화 → 원래 목적지로 재전송하는 과정이 추가되니까:

- **레이턴시 증가**: 원래 `나 → 목적지` 한 번이면 될 걸 `나 → VPN 서버 → 목적지`로 두 번 가야 하고, VPN 서버가 물리적으로 먼 나라에 있으면 체감이 커요
- **처리량(throughput) 감소**: 암호화/복호화 연산이 매 패킷마다 들어가고, 캡슐화로 패킷 크기도 커져서(헤더가 이중으로 붙으니까) 실질 대역폭이 줄어요
- **MTU 문제**: 원래 패킷에 VPN 헤더가 추가로 붙으면 패킷 크기가 네트워크가 허용하는 최대 크기(MTU)를 넘길 수 있어서, 패킷 단편화(fragmentation)가 발생하고 이게 성능을 더 떨어뜨려요

### 3. VPN 탐지 & 차단과의 싸움

VPN 원리가 단순한 만큼 **"이 트래픽이 VPN이다"라는 것도 탐지 가능**해요:

- 특정 VPN 서버 IP 목록을 차단 (넷플릭스가 이렇게 함)
- VPN 프로토콜 특유의 패킷 패턴을 **DPI(Deep Packet Inspection)**로 감지해서 차단 (중국 만리방화벽이 이 방식)
- 그래서 VPN 업체들은 트래픽을 일반 HTTPS처럼 위장하는 **난독화(obfuscation)** 기술을 쓰고, 차단하는 측은 더 정교한 탐지를 하고... 이게 계속 고양이-쥐 쫓기가 돼요

### 4. 신뢰 문제 — 기술이 아니라 사람의 문제

이게 제일 어려운 부분인데, VPN 업체가 "로그 안 남긴다"고 해도 검증 방법이 거의 없어요. 실제로 "no-log"를 주장하던 VPN 업체가 수사기관에 로그를 넘긴 사례도 있었고요. 기술적으로 완벽해도 **운영하는 주체를 신뢰할 수 있느냐**는 기술 밖의 문제예요.

---

정리하면 "봉투에 넣어서 대신 보내준다"는 아이디어 자체는 단순한데, 그걸 **빠르고, 안전하고, 탐지 안 되게, 신뢰할 수 있게** 구현하는 건 각각이 다 별도의 어려운 문제인 거예요.







# 디피-헬만 알고리즘

**키 자체를 전송하지 않고, 
양쪽이 각자 계산해서 같은 키를 독립적으로 만들어내는 것**이에요.

비유로 설명하면:

1. A가 **노란 물감**(공개값)을 공개적으로 보냄 — 누구나 볼 수 있음
2. A는 자기만 아는 **빨간 물감**(비밀값)을 섞어서 → **주황색**을 만들어 B에게 보냄
3. B는 자기만 아는 **파란 물감**(비밀값)을 섞어서 → **초록색**을 만들어 A에게 보냄
4. A는 받은 초록색에 자기 빨간 물감을 섞음 → **최종 색**
5. B는 받은 주황색에 자기 파란 물감을 섞음 → **같은 최종 색**

중간에서 엿보는 사람은 노란, 주황, 초록은 볼 수 있지만, **빨간/파란 물감을 모르니까 최종 색을 만들어낼 수 없어요.** 그리고 핵심은 "섞인 물감에서 원래 색을 분리하는 게 물리적으로 극도로 어렵다"는 점인데, 실제 디피-헬만에서는 이게 **이산 로그 문제(큰 소수에 대한 거듭제곱의 역연산)가 계산적으로 극도로 어렵다**는 수학적 성질로 보장돼요.

그래서 비밀 키가 네트워크를 한 번도 지나간 적이 없는데, 양쪽이 같은 키를 갖게 되는 거예요. critical section 비유로 돌아가면, "critical section 자체를 보호하는 문제"를 뮤텍스라는 하드웨어/원자적 연산으로 끊어낸 것처럼, 디피-헬만은 **"키를 전송한다"는 전제 자체를 없애버려서** 재귀를 끊은 거예요.

# JWT 원리는? 토큰 관리는 보안적으로 하는가?

### JWT는 이거랑 다른 개념이에요

JWT(JSON Web Token)는 "암호화된 통신 채널을 만든다"가 아니라 **"이 토큰이 위조되지 않았음을 증명한다"** 가 목적이에요.

구조는 이렇게 생겼어요:

```
헤더.페이로드.서명
(Base64).(Base64).(서명값)
```

- **헤더**: "이 토큰은 HS256 알고리즘으로 서명했어"
- **페이로드**: 실제 데이터 (예: `{"user_id": 42, "role": "admin", "exp": 만료시간}`)
- **서명**: 헤더+페이로드를 **서버만 아는 비밀키**로 서명한 값

중요한 건, **페이로드는 암호화가 아니라 Base64 인코딩일 뿐**이에요. 누구나 디코딩해서 내용을 읽을 수 있어요. JWT가 보장하는 건 **"이 내용을 누군가 몰래 바꾸지 않았다"** 는 무결성(integrity)이지, ><< 기밀성(confidentiality)이 아니에요. >> 내 생각과 다르게 보안이 아니었음.

서버가 검증하는 방식은:

1. 토큰을 받으면 헤더+페이로드 부분을 가져와서
2. 서버가 가지고 있는 비밀키로 같은 서명을 직접 다시 계산
3. 토큰에 붙어있는 서명과 비교 → 일치하면 "이건 내가 발급한 진짜 토큰" / 불일치면 "위조됨, 거부"

그래서 JWT는 **DB에 세션 저장 안 하고도 "이 유저가 로그인한 상태인지" 검증할 수 있는 방법**이에요. 서버가 매 요청마다 DB에서 세션을 조회할 필요 없이, 토큰의 서명만 검증하면 되니까 스케일이 좋아지죠.

### 정리

|목적|핵심|
|---|---|---|
|디피-헬만|안전한 키 교환|키를 전송하지 않고 양쪽이 독립적으로 같은 키를 계산|
|VPN/TLS|통신 내용 암호화|디피-헬만 등으로 만든 키로 전체 트래픽을 암호화|
|JWT|토큰 위조 방지|서명으로 "이거 내가 만든 거 맞아"를 증명 (암호화 아님)|

# 부팅 USB 의 역할

부팅 USB의 역할은 간단해요 
— **컴퓨터의 하드디스크/SSD 대신 USB에서 OS를 띄우는 것**이에요.

### 왜 필요한가

지금 상황을 생각해보면, Arch Linux를 설치하고 싶은데 아직 디스크 어디에도 Arch가 없잖아요. 그러면 **Arch를 설치해줄 프로그램 자체를 어디서 실행하냐**는 문제가 생겨요. 


윈도우 안에서는 Arch 설치를 할 수 없으니까, 윈도우도 아니고 Arch도 아닌 **임시 OS가 하나 필요한 거예요.**
=> OS를 설치하려면 이미 실행 중인 OS가 필요하다!!!!!
Arch 설치라는 건 결국 "디스크에 파티션 만들기 → 파일시스템 포맷 → 패키지 다운로드해서 복사 → 부트로더 설정" 같은 작업인데, 이걸 수행하려면 **커널이 돌아가고 있어야 하고, 네트워크도 되고, 디스크 쓰기도 되는 환경**이 필요함! (VM에 바로 iso 설치했던 건 VM이 가상 하드웨어를 에뮬레이션하기떄문이었음. 임시 OS를 부팅해주는 역할을 VM app 식으로 해줬던 것)
=> 실물 컴퓨터에서도 **완전히 똑같은 일**을 하는 건데, VM 대신 **실제 BIOS가 USB를 읽어서 부팅**하는 것만 다를 뿐이에요. "윈도우가 점유해서 못 깐다"는 것보다는, **윈도우가 실행 중인 상태에서 다른 파티션에 OS를 깔아주는 기능이 윈도우에 없기 때문**이에요. 윈도우 입장에서는 "남의 OS를 설치해주는 것"은 자기 역할이 아니니까요.


=> ### 설치해줄 프로그램"이 왜 따로 배포 안 되냐?

사실 우분투 같은 배포판은 **윈도우 안에서 실행 가능한 설치 프로그램(Wubi)** 이 예전에 있었어요. 근데 문제가 많아서 폐기됐고, Arch는 애초에 그런 걸 만들지 않았어요.

이유는 몇 가지가 있는데:

- **권한 문제**: 디스크 파티셔닝, 부트섹터 쓰기, 파일시스템 포맷 같은 작업은 **OS가 자기 디스크를 직접 제어하는 수준의 저수준 작업**이에요. 윈도우 위에서 실행되는 일반 프로그램이 이걸 하려면 윈도우의 디스크 관리자와 충돌할 수 있어요
- **Arch의 철학**: Arch는 의도적으로 "유저가 직접 하나하나 선택해서 설치"하는 방식을 유지하고 있어요. 그래서 GUI 설치 마법사도 공식적으로 안 만들고, 라이브 환경에서 커맨드라인으로 하는 게 공식 방법이에요
- **범용성**: USB 부팅 방식은 윈도우가 있든 없든, 디스크가 비어있든 아니든, 어떤 상황에서도 동작해요. "윈도우용 설치 프로그램"을 만들면 윈도우가 있는 환경에서만 쓸 수 있는 제한이 생기죠



부팅 USB가 바로 그 임시 OS 역할을 해요:

1. USB에서 부팅 → **RAM 위에 미니 리눅스가 올라감** (라이브 환경)
2. 이 임시 OS 안에서 디스크 파티셔닝, 포맷, 실제 Arch 시스템 설치를 수행
3. 설치 끝나면 USB 빼고 재부팅 → 이제 디스크에 설치된 진짜 Arch로 부팅

비유하면 **"집을 지을 때 쓰는 임시 컨테이너 사무실"** 같은 거예요. 집(Arch)이 아직 안 지어졌으니까, 공사 도구와 작업 공간이 필요한데 그걸 USB가 제공하는 거고, 집이 완성되면 컨테이너(USB)는 더 이상 필요 없어요.

### 아까 만든 윈도우 복구 USB도 같은 원리

윈도우가 부팅이 안 되는 상황이면, 윈도우 자체를 쓸 수 없으니까 **복구 USB에서 임시 OS(WinRE)를 띄워서** 거기서 복구 도구를 실행하는 거예요. 원리가 완전히 같아요.

즉 부팅 USB = **"디스크의 OS가 못 쓰거나 아직 없을 때, 대신 부팅해서 작업할 수 있게 해주는 임시 OS 매체"**예요.


# Rufus 없이 부팅 USB 만드는 방법들

몇 가지 방법이 있는데, 걸리는 시간은 다 비슷해요 (USB 쓰기 속도가 병목이라서). 차이는 **편의성**이에요.

#### dd 명령어 (리눅스/맥 터미널)

```bash
dd if=archlinux-x86_64.iso of=/dev/sdX bs=4M status=progress
```

이게 사실 가장 원시적인 방법인데, ISO 파일의 바이트를 **USB 디스크에 그대로 1:1로 복사**하는 거예요. 파일시스템이고 뭐고 없이 raw 바이트를 통째로 덮어써요. 시간은 USB 속도에 따라 2~5분 정도. 다만 디스크 이름(`sdX`)을 잘못 지정하면 **하드디스크를 통째로 밀어버릴 수 있어서** "disk destroyer"라는 별명이 있어요.

#### 윈도우 CMD로 수동 (Rufus 같은 툴 없이)

diskpart로 USB를 수동 포맷하고, ISO 내용을 복사하는 건데:

```
diskpart → list disk → select disk X → clean → 
create partition primary → active → format fs=fat32 quick →
assign → exit
```

그 다음 ISO를 마운트해서 파일을 USB로 복사. 
시간 자체는 5~10분 정도인데, **타이핑할 게 많고 실수 여지가 커요.** 
그리고 MBR/Legacy 부팅용으로 만들려면 `bootsect` 같은 추가 도구로 부트섹터를 따로 써줘야 하는 경우도 있어서 번거로워요.

#### balenaEtcher (GUI 툴, Rufus 대안)

Rufus랑 거의 같은데, 옵션이 더 적고 단순해요. 클릭 3번이면 끝. 시간도 동일.

### 결론

걸리는 시간은 어떤 방법이든 **USB 쓰기 속도에 의존**하니까 2~10분 정도로 거의 비슷해요. Rufus를 쓰는 이유는 빨라서가 아니라, **MBR/GPT 선택, 파티션 구성, 부트섹터 처리를 알아서 해주니까** 실수할 여지가 적어서예요. dd나 diskpart는 같은 결과를 내지만 사람이 직접 신경 써야 할 게 많아지는 거고요.


# 아치리눅스 부팅 후 윈도우 시간 달라지는 이유

### 원인: 하드웨어 시계(RTC)를 해석하는 방식이 다름

컴퓨터 메인보드에는 **RTC(Real Time Clock)** 라는 작은 시계가 있어요. 배터리(수은 전지)로 돌아가서 컴퓨터 꺼져도 시간이 유지되는 그 시계요. 문제는:

- **윈도우**: RTC에 저장된 시간을 **로컬 시간(한국시간, UTC+9)** 이라고 해석
- **리눅스**: RTC에 저장된 시간을 **UTC(세계 표준시)** 라고 해석

그래서 벌어지는 일이:


1. 윈도우가 RTC에 "23:00" 저장 (한국시간 밤 11시)
2. Arch로 부팅 → RTC의 "23:00"을 UTC로 읽음
3. Arch가 "아 지금 UTC 23:00이니까 한국시간은 +9해서 08:00이구나" → 정상 표시
4. Arch가 NTP(인터넷 시간 동기화)로 정확한 UTC를 받아서 RTC를 "14:00"(UTC)으로 수정
5. 윈도우로 돌아옴 → RTC의 "14:00"을 로컬 시간으로 읽음 → "오후 2시"로 표시
6. 실제로는 한국시간 밤 11시인데 오후 2시로 보임 → 딱 9시간 차이

한국이 UTC+9이니까 **정확히 9시간 차이**가 나는 거예요.



# VM은 sudo 가 필요하고, 지금 하는 세팅에서는 필요 없는 이유는?

### sudo 안 쓰는 이유 — 맞아요, 이미 root예요

프롬프트를 다시 보면:

```
root@archiso ~ #
```

- **root**: 지금 로그인된 유저가 root (= 최고 관리자)
- **#**: 프롬프트 끝이 `#`이면 root, `$`이면 일반 유저

Arch 라이브 환경은 **설치 작업 전용 환경**이라, 디스크 파티셔닝이나 포맷 같은 관리자 권한이 필요한 작업을 해야 하니까 **처음부터 root로 로그인된 상태**로 시작해요. << 일반 유저 계정 자체가 없어요. >> 

나중에 Arch 설치가 끝나고 실제 시스템으로 부팅하면, 그때는 일반 유저 계정을 만들고 필요할 때만 `sudo`를 쓰는 구조로 세팅하게 됩니다.




# 컴퓨터 강제 종료가 위험한 이유

### 1. 소프트웨어적 이유: 파일 시스템 파괴 💥 (가장 큰 위험)

운영체제(윈도우, 리눅스 등)는 사용자가 눈으로 보지 못하는 순간에도 백그라운드에서 끊임없이 데이터를 읽고 쓰고 있습니다.

- **정상 종료할 때:** OS가 _"자, 작업 완료했으니 파일 닫고, 임시 데이터 메모리에서 지우고, 저장장치에 '나 이제 끈다'고 기록(Flush)하자"_ 하고 **차근차근 마침표**를 찍고 끕니다.
    
- **강제 종료할 때:** 데이터를 한창 SSD/HDD에 기록하고 있는 도중에 전원이 통째로 날아갑니다.
    
    - 파일이 중간에 싹둑 잘리면서 **시스템 중요한 부팅 파일이나 데이터가 깨집니다.**
        
    - 결과적으로 다음 부팅 때 _"Boot Configuration Data is missing"_ 같은 검은 화면이 뜨거나 **부팅 불능 상태**가 됩니다.
        

### 2. 하드웨어적 이유: 저장장치(HDD/SSD) 손상 💾

- **옛날 HDD(하드디스크)의 경우:**
    
    HDD 내부에는 초당 수천 번 회전하는 원판(플래터)과 그 위를 미세하게 떠다니며 데이터를 읽는 바늘(헤드)이 있습니다. 강제 종료로 전원이 갑자기 끊기면 바늘이 원판을 긁어버리는 물리적 손상(배드섹터)이 생길 위험이 컸습니다.
    
- **요즘 SSD의 경우:**
    
    기계적인 바늘은 없어서 물리적 긁힘은 없지만, SSD 내부의 '매핑 테이블(데이터가 어디 저장되어 있는지 보여주는 지도)'이 순간적인 전원 차단으로 파손될 수 있습니다. 지도가 깨지면 SSD 전체를 인식하지 못하게 될 수도 있습니다.



# GB vs. GiB 복습

**GB**(Gigabyte)와 **GiB**(Gibibyte)는 모두 데이터의 용량을 나타내는 단위이지만, 기준으로 사용하는 단위 체계(10진법 vs 2진법)가 다릅니다.

## 핵심 차이점 한눈에 보기

| **구분**    | **GB (Gigabyte, 기가바이트)**   | **GiB (Gibibyte, 기비바이트)**    |
| --------- | -------------------------- | ---------------------------- |
| **단위 체계** | **10진법** (SI 표준)           | **2진법** (IEC 표준)             |
| **기준 값**  | $10^9 = 1,000,000,000$ 바이트 | $2^{30} = 1,073,741,824$ 바이트 |
| **용도**    | 저장장치 제조사(SSD, HDD), 통신사    | 운영체제(Windows), 메모리(RAM) 용량   |

## 왜 이런 차이가 생길까요?

- **10진법 단위 (GB):** 사람이 계산하기 쉬운 단위입니다.
    
    - $1\text{ KB} = 1,000\text{ Byte}$
        
    - $1\text{ MB} = 1,000\text{ KB}$
        
    - **$1\text{ GB} = 1,000\text{ MB} = 1,000,000,000\text{ Byte}$**
        
- **2진법 단위 (GiB):** 컴퓨터가 데이터를 처리하는 방식($2^n$)에 맞춘 단위입니다.
    
    - $1\text{ KiB} = 1,024\text{ Byte}$
        
    - $1\text{ MiB} = 1,024\text{ KiB}$
        
    - **$1\text{ GiB} = 1,024\text{ MiB} = 1,073,741,824\text{ Byte}$**
        

## 실제 표기 혼란: "500GB SSD를 샀는데 왜 465GB로 나올까?"

하드디스크나 SSD 제조사는 10진법 표기(GB)를 기준으로 표기하여 판매합니다. 하지만 **Windows 운영체제**는 내부적으로 2진법 계산(GiB)을 사용하면서도 표기는 'GB'로 그대로 표기하는 경우가 많습니다.

> **예시: 500GB SSD 표기 용량 차이**
> 
> - **제조사 기준:** $500\text{ GB} = 500,000,000,000\text{ Byte}$

> - **Windows 계산:** $500,000,000,000 \div 1,073,741,824 \approx \mathbf{465.66\text{ GiB}}$
>     
>     _(Windows 표기상 465GB로 보임)_
>     

이 때문에 용량이 줄어든 것처럼 보이지만, 실제 데이터 처리 바이트 수 자체는 동일합니다.

### 기타 단위 체계 비교

- **KB vs KiB:** 키로바이트($10^3$) vs 키비바이트($2^{10}$)
- **MB vs MiB:** 메가바이트($10^6$) vs 메비바이트($2^{20}$)
- **TB vs TiB:** 테라바이트($10^{12}$) vs 테비바이트($2^{40}$)






# 포맷이란

**"기존 내용을 무시하고, 파일시스템 자료구조를 새로 써넣는 것"** 이에요. 실제로 데이터를 물리적으로 지우는 게 아니라, **아이노드 테이블, 슈퍼블록, 블록 비트맵 같은 관리 구조를 새로 덮어쓰는 것**이에요. 

그래서 "빠른 포맷"이 빠른 거예요 — 수백 GB의 데이터를 하나하나 지우는 게 아니라 관리 장부만 새걸로 교체하니까요. (원래 데이터는 물리적으로 남아있어서 <<복구 프로그램으로 살릴 수 있는 경우가 있는 것도 이 때문>> 이에요)

### 이미 있던 파일시스템 바꿀 때도 포맷이라 하냐 → 네

- NTFS → ext4로 바꿀 때: `mkfs.ext4`로 포맷 (기존 NTFS 구조를 무시하고 ext4 구조를 새로 써넣음)
- ext4 → ext4로 다시 할 때: 같은 타입이어도 포맷이라고 함 (관리 구조를 초기화하니까)
- 윈도우에서 USB "포맷"하는 것도 같은 원리 — FAT32/NTFS/exFAT 중 하나의 파일시스템 구조를 새로 써넣는 거예요




# ext4 가 리눅스의 보편적 FS라면 NTFS는 윈도우?

**NTFS = New Technology File System**. 마이크로소프트가 만든 윈도우 전용 파일시스템이에요. 리눅스에서도 읽고 쓸 수는 있지만(ntfs-3g 드라이버로), 네이티브가 아니라 성능이 떨어져요.

주요 파일시스템을 정리하면:

| 파일시스템         | 주 사용처                    |
| ------------- | ------------------------ |
| NTFS          | 윈도우                      |
| ext4          | 리눅스                      |
| APFS          | macOS                    |
| FAT32 / exFAT | USB, SD카드 등 범용 (어디서든 읽힘) |



# 루트 유저의 구체적인 의미

### root — 두 가지 의미가 있어요

"root"라는 단어가 리눅스에서 **두 가지 다른 뜻**으로 쓰여서 헷갈리기 쉬운데:

#### 1. root 유저 (UID 0)

말씀하신 대로 **최고 관리자 계정**이에요. 모든 파일을 읽고 쓸 수 있고, 모든 프로세스를 죽일 수 있고, 디스크를 포맷할 수도 있어요.

`chmod`로 권한을 바꾸는 것도 root가 하는 거고, root 자신은 **파일 권한(rwx)을 무시하고 접근할 수 있어요.** 그래서 위험한 거예요 — 실수로 `rm -rf /` 같은 걸 치면 시스템이 통째로 날아가니까, 평소에는 일반 유저로 쓰고 필요할 때만 `sudo`로 root 권한을 빌려 쓰는 거예요.

#### 2. 루트 디렉토리 (`/`)

파일시스템의 **최상위 디렉토리**예요. 모든 경로의 시작점이에요:

```
/                  ← 루트 디렉토리 (이게 꼭대기)
├── bin/           ← 실행 파일들
├── etc/           ← 설정 파일들
├── home/          ← 일반 유저들의 홈 디렉토리
├── boot/          ← 커널, 부트로더
├── dev/           ← 장치 파일들 (아까 본 /dev/sdb 등)
├── mnt/           ← 임시 마운트 포인트 (지금 여기에 sdb2 마운트함)
└── ...
```

"루트"라는 이름인 이유는 **트리 자료구조의 루트 노드**와 같은 개념이라서예요. 모든 디렉토리/파일이 이 `/`에서 뻗어나가는 구조.

두 개는 완전히 별개 개념인데 같은 단어를 쓰는 거예요. "root 유저의 홈 디렉토리"는 `/root`이고, "루트 디렉토리"는 `/`이고 — 헷갈리게 만든 건 역사적 네이밍 문제예요.






# sudo rm -rf 하면 OS까지 날아가나? 파일정보만 날아가나?

### rm -rf로 OS 설정도 날아가나

**root 권한으로 `rm -rf /` 치면 OS 자체도 날아가요.** 
OS도 결국 `/bin`, `/etc`, `/boot` 안에 있는 파일들이니까, root 권한이면 그것도 지워버려요. 

실행 중인 커널은 이미 RAM에 올라가 있어서 바로 멈추진 않지만, 시스템 파일이 하나둘 지워지면서 명령어도 안 되고, 재부팅하면 커널 파일 자체가 없으니 부팅도 안 되는 상태가 돼요. 

참고로 요즘 리눅스는 `rm -rf /`를 치면 **안전장치가 작동해서 거부**해요. `--no-preserve-root` 옵션을 일부러 붙여야 실행되게 막아뒀어요.





# GRUB

### GRUB이란

**GRUB = GRand Unified Bootloader**. 이름 그대로 **부트로더**예요.

아까 OS 설치 단계에서 "정문에 안내 표지판을 세우는 것"이라고 비유한 그거예요. 컴퓨터 전원이 켜지면 이런 순서로 진행되는데:

```
전원 ON
  → CPU가 BIOS 실행 (메인보드 ROM에 있음)
  → BIOS가 "어느 디스크에서 부팅할까?" 결정
  → 그 디스크의 첫 섹터(MBR, 512바이트)를 읽음
  → 여기에 GRUB 코드가 있으면 GRUB이 실행됨
  → GRUB이 커널 파일(/boot/vmlinuz)을 찾아서 RAM에 올림
  → 커널이 나머지 OS를 시작
```

즉 GRUB은 **BIOS와 커널 사이의 다리** 역할이에요. BIOS는 "디스크 첫 섹터에 있는 프로그램을 실행해"까지만 해주고, 그 프로그램(GRUB)이 "커널이 디스크 어디에 있는지 알아내서 RAM에 올려주는" 일을 해요.

### 지금까지 GRUB 없이도 Arch 라이브 환경에 들어갈 수 있었던 이유

USB에는 **USB 자체의 부트로더**가 이미 들어있어서 (==Rufus가 ISO 구울 때 같이 넣어줬어요)==, BIOS가 USB의 MBR을 읽으면 그 부트로더가 ISO 안의 커널을 RAM에 올려줬던 거예요.

하지만 디스크에 설치한 Arch는 아직 **자기만의 부트로더가 없어요.** 그래서 지금 상태로 USB 없이 디스크 1(sdb)로 부팅하려고 하면 BIOS가 sdb의 MBR을 읽는데, 거기에 아무것도 없으니까 부팅이 안 돼요. GRUB을 설치하면 sdb의 MBR에 "커널은 이 파티션의 이 경로에 있어"라는 정보가 쓰여져서, 그때부터 USB 없이도 직접 부팅 가능해지는 거예요.






# fstab 이란?

### fstab이 뭐냐

**fstab = file system table**. 말 그대로 **"파일시스템 표"** 예요.

아까 `mount /dev/sdb2 /mnt` 명령으로 파티션을 직접 마운트했잖아요. 그건 **수동으로 한 번만** 연결한 거라, 재부팅하면 풀려요. fstab은 **"부팅할 때마다 자동으로 이 파티션을 이 경로에 마운트해줘"라고 적어두는 설정 파일**이에요.

내용은 대충 이렇게 생겼어요:

```
# <파티션(UUID)>       <마운트 위치>  <파일시스템>  <옵션>
UUID=a1b2c3d4-xxxx-xxxx   /          ext4       defaults  0 1
```

이게 없으면 Arch가 부팅될 때 **"내 루트 파티션이 어디야?"를 모르니까** 부팅이 안 돼요. 그래서 `genfstab` 명령으로 현재 마운트 상태를 읽어서 이 파일을 자동 생성해주는 거예요.



# 파티션을 나누고, 할당해야 하는 이유


좋은 질문이에요. 
이걸 이해하면 아까 설명한 "OS 설치 = 파일시스템 만들기"가 더 선명해져요.

### 지금 라이브 환경의 상태

지금 부팅 USB에서 돌아가는 Arch 라이브 환경은 **RAM 위에서만 동작**해요. 파일을 만들 수도 있고 명령어도 실행할 수 있지만, 그건 전부 RAM에 임시로 존재하는 거라 **재부팅하면 전부 사라져요.** 영구적으로 저장할 "집"이 없는 상태예요.

### ==파티셔닝이 왜 필요한가==

디스크는 원래 그냥 **수십억 개의 바이트가 일렬로 늘어선 배열**이에요. 이 상태로는 OS가 "파일을 어디에 저장해야 할지" 알 수가 없어요. 단계별로 보면:

**파티셔닝 전 — 미할당 공간:**

```
[????????????????????????????????????????]
그냥 빈 바이트 덩어리. 아무 구조도 없음.
"여기가 뭔지" 아무도 모름.
```

**파티셔닝 후 — 구역이 생김:**

```
[sdb1: NTFS (F:드라이브)] [sdb2: 여기는 Linux용]
경계선이 생기고, 각 구역의 시작/끝 위치가 파티션 테이블에 기록됨.
하지만 sdb2 안은 아직 빈 바이트 덩어리.
```

**포맷(mkfs) 후 — 파일시스템이 생김:**

```
[sdb1: NTFS] [sdb2: ext4 (아이노드 테이블, 슈퍼블록, 루트 디렉토리 등)]
이제 sdb2 안에 "파일"이라는 개념이 존재함.
파일을 만들고, 읽고, 쓸 수 있는 구조가 갖춰짐.
```

**시스템 파일 복사 후 — OS가 존재함:**

```
[sdb1: NTFS] [sdb2: ext4 (커널, 라이브러리, bash, pacman...)]
이제 여기서 << 부팅할 수 있는 OS >> 가 됨.
```

### 비유로 정리하면

| 단계       | 비유                 | 없으면?                      |
| -------- | ------------------ | ------------------------- |
| 미할당 공간   | 허허벌판               | 아무것도 못 함                  |
| 파티셔닝     | "여기부터 여기까지 내 땅" 등기 | 땅 경계가 없으니 건물을 지을 수 없음     |
| 포맷(mkfs) | 도로/주소 체계 설치        | 주소가 없으니 "어디에 뭘 놓을지" 관리 불가 |
| 파일 복사    | 건물 짓기              | 빈 도시                      |
| 부트로더     | 정문 표지판             | 도시가 있는데 입구를 못 찾음          |

그래서 파티셔닝은 **"이 바이트 공간을 사용 가능한 구역으로 등록하는 첫 번째 단계"** 예요. 이게 있어야 그 위에 파일시스템을 올릴 수 있고, 파일시스템이 있어야 파일을 저장할 수 있고, 파일이 있어야 OS가 존재할 수 있어요.


# ISO 가 CLI 를 띄워주는 원리

ISO 안에는 **완전한 리눅스 커널 + 최소한의 유저 공간 프로그램**이 들어있어요. 부팅 과정을 따라가보면:

1. BIOS가 USB의 부트섹터를 읽음
2. 부트로더(syslinux/GRUB)가 **커널(vmlinuz)** 을 RAM에 올림
3. 커널과 함께 **initramfs**(초기 RAM 파일시스템)도 RAM에 올림 — 이 안에 최소한의 디렉토리 구조(`/bin`, `/dev`, `/etc` 등)와 드라이버들이 압축되어 들어있어요
4. 커널이 initramfs를 풀어서 RAM 위에 루트 파일시스템을 만듦
5. 그 안에서 **init 프로세스** 실행 → 이게 나머지 초기화(네트워크, 장치 인식 등)를 하고
6. 마지막에 `/bin/bash`(셸)를 실행 → **그게 지금 보고 있는 `root@archiso ~ #` 프롬프트**

즉 CLI가 "특별히 띄워지는 것"이 아니라, **커널이 부팅되고 init이 실행되고 셸이 뜨는 정상적인 리눅스 부팅 과정 그 자체**예요. 디스크에 설치된 리눅스가 부팅되는 것과 원리가 100% 같고, 차이는 루트 파일시스템이 디스크가 아니라 **RAM 위에 있다**는 것뿐이에요.

### ISO = 최소한의 툴, 나머지는 네트워크로 → 맞아요

정확한 이해예요. Arch ISO 안에 들어있는 건:

- 커널 + 드라이버
- 셸(bash), 파티셔닝 도구(fdisk), 포맷 도구(mkfs), 네트워크 도구
- **패키지 매니저(pacman)** — 이게 핵심이에요

실제 OS를 구성하는 수천 개의 패키지는 ISO 안에 없고, `pacstrap` 명령을 실행하면 pacman이 **미러 서버에서 인터넷으로 다운로드**해서 디스크에 설치해요. 그래서 Arch 설치에 인터넷이 필수인 거예요.

반면 우분투 ISO는 반대 철학인데, 대부분의 패키지를 **ISO 안에 미리 다 넣어둬서** 오프라인 설치도 가능해요. 그래서 우분투 ISO가 4~5GB이고 Arch ISO는 1GB 미만인 거예요.

OS 설치가 뭔지를 제대로 이해하려면, 먼저 
**"OS가 뭘 하는 물건인지"** 부터 거꾸로 생각하면 돼요.

### OS란 결국 뭐냐

컴퓨터가 켜지면 CPU는 **메모리의 특정 주소에서 명령어를 읽어서 실행**하는 것밖에 못 해요. OS는 그 "명령어 묶음"이에요. 구체적으로:

- **커널(kernel)**: 하드웨어를 직접 제어하는 프로그램. 메모리 관리, 프로세스 스케줄링, 디스크 I/O, 네트워크 등

# 커널 이해 심화..

=> 커널 = ASM 이랑가장가까운거아님?
하드웨어직접제어니까.....하 어렵네
커널이그럼뭐하는거지;;;????
리눅스커널보면 C, Rust 같은 저수준에가까우나 컴파일기반언어인고수준언어들이 같이 들어있는데
어케하는거임이건??


=> **커널은 어셈블리보다 C 언어나 Rust 같은 언어에 훨씬 가까우며, 실제로 리눅스 커널의 95% 이상은 C 언어로 작성**되어 있습니다. (최근에는 안전성을 위해 Rust도 도입되고 있죠!)

이게 어떻게 가능한지, 커널이 정확히 무슨 일을 하는지 핵심만 쉽게 짚어드릴게요.

## 1. 커널은 어셈블리가 아니라 왜 C/Rust로 만들었을까?

하드웨어를 제어하는 데는 **C 언어**만으로도 충분히 깊게 접근할 수 있습니다. C 언어는 메모리 주소에 직접 접근(포인터)하고, 하드웨어 레지스터 제어 명령을 내릴 수 있는 능력이 있거든요.

- **100% 어셈블리로 짜면 어떤 일이 벌어질까?**
    
    - CPU 가 바뀔 때마다(Intel $\rightarrow$ ARM $\rightarrow$ RISC-V) 커널 코드를 전부 다시 짜야 합니다.
        
    - 코드 길이가 무시무시하게 길어지고, 사람이 읽고 유지보수하기가 거의 불가능해집니다.
        
- **C / Rust 언어로 짜면?**
    
    - 사람이 읽기 편한 고수준/중수준 코드로 작성합니다.
        
    - 컴파일러(GCC, Clang 등)가 해당 CPU(Intel, ARM 등)에 맞는 어셈블리/기계어로 알아서 번역(컴파일)해 줍니다.
        
    - 단, << CPU가 시작될 때 아주 극초기화 부분이나 C언어로 표현이 안 되는 특수 CPU 명령어(몇 % 안 됨)만 어셈블리로 적고, 나머지는 다 C/Rust로 처리합니다. >>
        

## 2. 그럼 커널이 대체 하는 일이 뭔가요?

- **보안 및 권한:** "너 일반 사용자 프로그램인데 감히 시스템 중요한 파일 삭제하려고 해? 거절!"
    

## 3. 한눈에 보는 컴퓨터 구조

우리가 만드는 일반 앱과 하드웨어 사이의 관계는 이렇게 생겼습니다.

[ 사용자 애플리케이션 (웹 브라우저, 게임, 파이썬 등) ]

> **핵심 요약:**
>

어셈블리로 이 거대하고 복잡한 시스템 관리 로직을 다 짜려면 인류의 생산성으로는 불가능했을 겁니다. C 언어가 대단한 이유가 바로 "사람이 이해하기 쉬운 문법을 쓰면서도 하드웨어를 직접 건드릴 수 있는 힘"을 가졌기 때문입니다!

## 1. 컴파일러는 대체 어디에 있는 거죠?

컴파일러도 그냥 하나의 일반적인 소프트웨어(프로그램)일 뿐입니다!

우리가 흔히 쓰는 `gcc`, `clang`, `javac` 같은 컴파일러들은 운영체제(OS/커널) 위에서 실행되는 '유저 영역 프로그램'입니다. 메모장에 짠 `test.c`라는 글자(텍스트 파일)를 읽어들여서, CPU가 읽을 수 있는 `test.o` 또는 `a.out`이라는 기계어(바이너리 파일)로 변환해 내보내는 '문자열 변환 프로그램'인 셈이죠.


```
[ 유저 공간 (User Space) ]
  ├── 카카오톡, 웹 브라우저
  └── 컴파일러 (GCC, Clang 등)  <-- C/C++로 짜인 그냥 프로그램!
─────────────────────────────────────────────────────────────
[ 커널 공간 (Kernel Space) ]
  └── Linux / Windows 커널
─────────────────────────────────────────────────────────────
[ 하드웨어 (Hardware) ]
  └── CPU, RAM, Disk
```

## 2. 컴파일러의 역사: 최초의 C 컴파일러는 어떻게 만들어졌을까?

질문하신 "최초의 도구는 어떻게 만들었는가?"에 대한 답입니다. 정확히 짚으신 단계별 과정을 거쳤습니다.

### 1단계: Pure 기계어 (0과 1)

컴퓨터의 극초기에는 컴파일러도, 어셈블러도 없었습니다. 엔지니어들이 스위치를 올렸다 내리거나 타 punch card에 구멍을 뚫어 **`01001011` 같은 기계어를 사람이 직접 손으로 작성**했습니다.

### 2단계: 최초의 어셈블러 (Assembler)

`01001011` 같은 숫자를 외우기 너무 힘드니, `MOV`, `ADD` 같은 단어로 적는 어셈블리(ASM)를 만들었습니다. (문자 = 아스키코드 = 문자하나당 숫자하나 매핑한 테이블임. )
1960년대 미국 표준 협회(ANSI)에서 통신 장비(전신기 등)끼리 문자를 주고받기 위해 모여서 합의했습니다.

- `0100 0001` (십진수 65) $\rightarrow$ **'A'** 라고 정하자!
    
- `0100 0010` (십진수 66) $\rightarrow$ **'B'** 라고 정하자!
    
- `0010 0000` (십진수 32) $\rightarrow$ **'공백(Space)'** 으로 정하자!
    

컴퓨터 입장에서는 여전히 'A'라는 문자를 모릅니다. 단지 **65라는 숫자(`01000001`)를 다룰 뿐**입니다.

- 최초의 어셈블러 프로그램은 **사람이 직접 0과 1(기계어)로** 짜서 만들었습니다.

- 이제부터는 어셈블리로 코드를 적고, 이 어셈블러를 돌려 기계어로 바꿀 수 있게 됩니다.


문자-숫자 매핑을 어떻게 "HW적으로 박아넣었을까?"

"숫자 `01000001`이 들어왔을 때 화면에 **A** 모양을 그리는 과정"을 보면 하드웨어에 어떻게 박혀있는지 이해가 됩니다.

극초기 컴퓨터나 모니터의 하드웨어에는 글꼴 ROM (Font ROM)이라는 회로 칩이 물리적으로 박혀 있었습니다.


```
[키보드 눌림] 
      │
      ▼
 키보드 회로가 'A' 키에 해당하는 전압 신호(01000001) 발생
      │
      ▼
 [ 하드웨어 (Font ROM / 비디오 칩셋) ]
 01000001 (65) 번지 주소로 전기가 들어감!
      │
      ▼
 해당 번지에 픽셀로 'A' 모양이 그려진 스위치 회로가 켜짐!
 ◼◼◼◼◻
 ◼◻◻◼◻
 ◼◼◼◼◻
 ◼◻◻◼◻
      │
      ▼
 모니터 화면의 해당 위치 전극에 전기가 통하며 'A' 모양으로 빛이 남!
```

즉, 소프트웨어가 해석한 게 아니라, **"65라는 신호(전압)가 들어오면 'A' 글자 모양 형태로 배치된 전자 회로로 전기가 흐르게" 하드웨어를 설계**해 둔 것입니다.

=> 그럼 어셈블러는 문자를 어떻게 처리했을까요?

최초의 어셈블러를 만들 때 개발자(사람)는 아스키 코드 표를 옆에 두고 이렇게 기계어를 작성했습니다.

1. 사용자가 키보드로 `MOV`라는 글자를 입력하면, 키보드 회로는 아스키 코드에 따라 `77(M), 79(O), 86(V)`에 해당하는 이진수 전압 신호를 컴퓨터에 보냅니다.
    
2. 어셈블러 프로그램(기계어)은 메모리에 들어온 신호가 `77, 79, 86` 순서로 늘어서 있는지 비교합니다.
    
3. "어? `77-79-86`이 연속으로 들어왔네? 이건 CPU의 `01001011` 명령어로 번역해야지!" 하고 매칭시켜 준 것입니다.



### 3단계: C 언어 이전의 언어 (B 언어 등)

어셈블리로 매번 코딩하려니 너무 피곤해서, 조금 더 사람 언어에 가까운 언어(B언어 등)를 만들었습니다.

- B 언어 컴파일러를 **어셈블리(ASM)로** 작성했습니다.


### 4단계: C 언어 컴파일러의 탄생 (부트스트랩)

데니스 리치(Dennis Ritchie)가 C 언어를 만들었을 때의 순서입니다.

1. **C 언어 컴파일러 1호기(극초기 버전):** 기존에 있던 B 언어나 어셈블리로 만들었습니다.
    
2. **C 언어 컴파일러 2호기:** 1호기 C 컴파일러가 완공되자, 이제 **컴파일러 자체의 소스코드를 C 언어로 다 바꿉니다.**
    
3. 2호기 C 코드를 **1호기 컴파일러에 넣고 돌려서** C 언어로 만든 C 컴파일러 실행 파일(바이너리)을 완성합니다!
    

> **부트스트랩(Bootstrapping)이란?**
> 
> "장화 끈(Bootstrap)을 잡아당겨 스스로 공중에 뜨다"라는 뜻으로, 아주 작은 최소한의 도구(어셈블리)로 다음 단계 도구(C)를 만들고, 그 도구로 자기 자신을 발전시켜 나가는 과정을 말합니다.

- **시스템 유틸리티**: 커널 위에서 돌아가는 기본 도구들 (파일 복사, 텍스트 편집, 네트워크 설정 등)
- **라이브러리**: 다른 프로그램들이 공유해서 쓰는 코드 (glibc, libstdc++ 등)
- **부트로더**: 전원 켜졌을 때 "커널을 메모리에 올려주는" 첫 번째 프로그램

이게 전부 **파일**이에요. 

커널도 파일(`/boot/vmlinuz`), 유틸리티도 파일(`/bin/ls`, `/bin/bash`), 라이브러리도 파일(`/lib/libc.so`). 결국 OS = **특정 디렉토리 구조 안에 특정 파일들이 특정 위치에 놓여있는 상태**예요.

---
### 그래서 "OS를 설치한다" = 이 상태를 만드는 것

단계별로 보면:

#### 1단계: 파티션 생성 — "땅을 구획하는 것"

디스크는 원래 그냥 거대한 바이트 배열이에요. 파티셔닝은 이 바이트 배열의 **"여기부터 여기까지는 A 구역"** 이라고 메타데이터(파티션 테이블)를 디스크 맨 앞에 기록하는 거예요. (파일정보저장 그거랑 똑같음 어차피 모든게 파일이니까. dir조차도,..)

- MBR 방식: 디스크의 첫 512바이트(섹터 0)에 파티션 테이블 저장. 항목 4개까지
- GPT 방식: 더 큰 헤더 영역에 128개까지 저장 가능

이 시점에서 파티션은 **빈 바이트 공간**일 뿐이에요. 아직 파일이라는 개념이 없어요.

#### 2단계: 파일시스템 포맷 — "빈 땅에 주소 체계를 만드는 것"

`mkfs.ext4 /dev/sda1` 같은 명령을 실행하면, 그 파티션의 바이트 공간에 **파일시스템의 자료구조**를 써넣어요:

- **슈퍼블록**: "이 파일시스템은 ext4이고, 전체 크기는 X이고, 블록 크기는 4KB이고..." 같은 메타정보
- **아이노드 테이블(inode table)**: 파일 하나당 아이노드 하나. 파일의 크기, 권한, "데이터가 디스크의 어느 블록에 있는지"를 기록하는 구조체
- **블록 비트맵**: 어떤 블록이 사용 중이고 어떤 블록이 비어있는지 추적
- **루트 디렉토리(`/`)**: 최상위 디렉토리의 아이노드 생성

이게 끝나면 이제 **"이 파티션 안에 파일을 만들고 읽고 쓸 수 있는 상태"** 가 된 거예요. 비유하면 빈 땅에 도로 체계와 주소 번호를 부여한 것과 같아요. 아직 건물(파일)은 하나도 없지만, 건물을 지을 수 있는 인프라가 갖춰진 거죠.

#### 3단계: 시스템 파일 복사 — "건물을 짓는 것"

Arch에서는 `pacstrap /mnt base linux linux-firmware` 같은 명령으로 이 작업을 해요. 이게 하는 일은:

- 패키지 매니저(pacman)가 **미러 서버에서 패키지(.tar.zst 파일)를 다운로드**
- 압축 해제해서 **마운트된 파티션의 올바른 경로에 파일을 배치**

```
/mnt/boot/vmlinuz-linux    ← 커널 이미지
/mnt/boot/initramfs-linux.img  ← 초기 RAM 디스크
/mnt/bin/bash              ← 셸
/mnt/lib/libc.so           ← C 라이브러리
/mnt/etc/fstab             ← 파일시스템 마운트 설정
... (수천 개의 파일)
```

이 시점에서 **디스크에 OS의 모든 파일이 물리적으로 존재**해요. 하지만 아직 부팅은 안 돼요 — 컴퓨터가 켜졌을 때 "이 커널을 메모리에 올려라"라고 알려주는 장치가 없으니까요.

#### 4단계: 부트로더 설치 — "정문에 안내 표지판을 세우는 것"

GRUB 같은 부트로더를 설치하면, **디스크의 부트 영역에 작은 프로그램**이 써져요. 컴퓨터 전원이 켜지면:

```
전원 ON
  → CPU가 BIOS/UEFI 펌웨어 실행 (메인보드 ROM에 있음)
  → BIOS가 디스크의 첫 섹터(MBR) 읽음
  → 거기에 GRUB의 1단계 코드가 있음
  → GRUB이 나머지 자신을 로드
  → GRUB이 커널 파일(/boot/vmlinuz)을 찾아서 RAM에 올림
  → 커널에 제어권 넘김
  → 커널이 하드웨어 초기화, init 프로세스 시작
  → OS 부팅 완료
```

#### 5단계: 시스템 설정 — "건물 안 배선/배관 연결"

- `fstab`: "부팅할 때 어떤 파티션을 어디에 마운트할지" 설정
- 네트워크 설정, 시간대, 로케일(언어), 호스트네임 등
- 유저 계정 생성, 비밀번호 설정

### 정리하면

|단계|하는 일|비유|
|---|---|---|
|파티셔닝|디스크에 구역 경계선 기록|빈 땅에 구획을 나눔|
|포맷|파일시스템 자료구조 생성|도로/주소 체계를 깔음|
|파일 복사|커널, 라이브러리, 도구들을 디스크에 배치|건물을 지음|
|부트로더|전원 ON 시 커널을 찾아 RAM에 올리는 코드 설치|정문 안내 표지판|
|설정|fstab, 네트워크, 유저 등|배선/배관 연결|

결국 **OS 설치 = "빈 디스크 공간에 파일시스템을 만들고, 거기에 OS 파일들을 올바른 위치에 배치하고, 부팅 경로를 설정하는 것"**이에요. 우분투 같은 배포판은 이 전 과정을 GUI 마법사가 자동으로 해주는 거고, Arch는 이걸 한 단계씩 직접 하는 거예요. 그래서 Arch 설치가 오래 걸리지만, 그 과정에서 OS가 실제로 뭘로 이루어져 있는지를 체감하게 돼요.
